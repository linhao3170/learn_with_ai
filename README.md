# LearnWithAI · 项目业务逻辑分析与教学辅助引擎

> **一句话定位：我们不比大模型更聪明，我们让大模型的输出变得可复现、可追溯、可被教师改写。**
>
> 给它一个真实项目，还你一套能直接上课、且每条结论都能回指到代码行的教学材料。

## 一、核心定位（反复确认，防止跑偏）

> ❌ 不是：学生刷题的做题平台
>
> ❌ 不是：测代码能不能跑通的 OJ 系统
>
> ❌ 不是：又一个 AI 代码解释器
>
> ❌ 不是："比 ChatGPT 分析得更准"的工具 —— **我们赢不了这条，也不该往这条上撞**
>
> ✅ **是：一条从代码到题目到答案的可追溯、可复现、可被教师改写的证据链**
>
> ✅ **是：教师的项目教学材料生成器 —— 上传项目，出全套教学内容**
>
> ✅ **是：项目级业务逻辑分析引擎 —— 结构化、有证据、可审核**

### 为什么不是"我们更准"

因为"更准"是一条注定失败的赛道。GPT-5 级别的模型读一遍代码，语义理解能力大概率强于我们 7000 行的启发式规则引擎。

**但大模型有三件事在架构上永远做不到：**

1. **可复现** —— 同一个项目问一百次，它给一百个略有差异的答案。我们的规则引擎给同一个答案。
2. **可定位** —— 它说"这个模块负责预约管理"，你说不清依据是哪几行。我们每条结论带 `filepath:line`。
3. **可沉淀** —— 它不知道"上一届老师改过这条结论、说过这句话不能这么讲"。我们的审核结果可以固化，下次重新生成不丢。

**这三件事就是护城河。所有对外表述都必须围绕它们展开，而不是围绕"准确率"。**

## 二、必须先承认的现实：这个问题不该急着做成平台

### 2.1 判断一个能力该不该做成平台，只有一条尺子

> **如果一份提示词 + 一个脚本就能交付，它就不该是平台。**

用这条尺子量我们自己的功能：

| 能力 | 正确形态 | 理由 |
|------|---------|------|
| 生成一份项目分析报告 | **Skill / CLI** | 一次性、无状态、不需要沉淀 |
| 教案导出 PPT / Word | **Skill** | 模板化输出，无跨会话状态 |
| 学生答题 + 数据回流 | **平台** | 需要跨人、跨时间、跨班级的状态 |
| 一个班 40 份作业的一致性批改 | **平台** | 必须共享同一份事实基线 |
| 教师审核界面 + 修改固化 | **平台** | 需要 UI 和持久化 |
| 项目案例库检索 | **平台** | 需要索引和复用 |

**结论：我们现在有一半的功能应该先做成 Skill。** 平台化不是目的，是 Skill 验证失败之后的必然结果。

### 2.2 所以第一件事是"证明平台是必要的"

不要先写平台，先写 Skill，然后用它去打真实项目。**哪一边崩了，都是收获：**

- **Skill 就够用** → 省下三个月的平台开发，直接交付。
- **Skill 崩了** → 你拿到了"为什么必须是平台"的实证。

大模型有一个硬性物理限制，是我们最好的论据：

> **一个 20 万行的 Spring Boot 项目塞不进上下文窗口。**
> 塞不进去它就会编。而我们的引擎做**一次结构化索引**，之后复用一万次 —— 索引里没有的东西，我们不说。

### 2.3 但平台确实有它才能做的事

Skill 版本在下面这些场景会失效，这些**就是平台的立项理由**：

1. 大项目超出上下文 → 分析一次，稳定复用
2. 需要行号证据 → 前端代码并排对照
3. 教师修改需要固化 → 下次重新生成不能覆盖
4. 需要看班级学情 → 答题数据必须存下来
5. 需要私有化部署 → 校内网络、数据不出校

## 三、必须解决的三个痛点（按优先级）

### 痛点 1：如何证明"不用平台"不行 —— 必须拿出实证，不能靠嘴说

**这是立项的第一道关，也是评委的第一个问题。**

不能停在"我们的结构化输出更好"这种话上，因为多写几句提示词就有了。必须拿出**可重复、可复核的实测对比**。

**要产出的东西：一份《Skill 失效点实测报告》，包含：**

| 实测维度 | 怎么测 | 期望的失效证据 |
|---------|--------|--------------|
| **一致性** | 同一项目、同一个问题，纯 Prompt 问 10 次 | 10 次答案有 N 处不一致，逐处列出 |
| **可定位性** | 对比两者对"某模块的职责"的回答 | 纯 Prompt 说不清依据在哪几行 |
| **大项目** | 拿一个 >5 万行的真实项目 | 纯 Prompt 超出上下文，开始编造不存在的类和方法 |
| **可改写** | 教师改一条结论，重新生成 | 纯 Prompt 完全丢失修改 |
| **批量一致性** | 同一份基线批改 40 份作业 | 纯 Prompt 每次评分尺度漂移 |

**验收标准**：能指着报告里的一条具体记录，说出"这一条纯 Prompt 做不到，我们的做法是这样"。
**如果实测下来纯 Prompt 全都做到了 —— 那就应该停掉这个项目，或者只做 Skill 版本。这是必须接受的结论。**

### 痛点 2：业务逻辑的可靠性 —— 必须做"可信度分级"，否则第三层就是编

**这是引擎目前最大的硬伤，必须当众承认。**

看现在的 [engine/deep_analyzer/key_implementation.py:496-559](engine/deep_analyzer/key_implementation.py#L496-L559)：

```python
# 现状：按方法名关键词贴标签
if any(w in name_lower for w in ("check", "validate", "verify")):
    action_label = "validation / verification"
elif "conflict" in name_lower:
    action_label = "conflict detection"
```

`_infer_algorithm_type`（[同文件 572-592](engine/deep_analyzer/key_implementation.py#L572-L592)）也一样 —— **方法名里出现 `conflict` 就报 "interval overlap detection"。**

**这在教师眼里是"看着像分析，实际是模板"，而且穿帮一次，整个项目的信任就没了。**
[engine/deep_analyzer/design_pattern_detector.py](engine/deep_analyzer/design_pattern_detector.py)（1037 行）是最大的误报来源 —— 从代码结构猜设计模式，误报率天然很高。

**修法：给每一条结论强制标注可信度等级，并在 UI 上诚实展示。**

| 等级 | 含义 | 典型内容 | UI 展示 |
|------|------|---------|--------|
| **确定（verified）** | 从 AST 直接读出，可复现 | 调用链、行号、依赖次数、状态读写、raise 的异常类型、守卫条件 | 正常展示，绿色 |
| **推断（inferred）** | 有依据地推的，**必须附依据** | "此方法含 3 处前置校验 + 2 处异常抛出，推断为校验型实现（依据：行 76/83/88）" | 黄色，依据可点击 |
| **待确认（unconfirmed）** | 语义归纳，需教师确认 | 模块职责命名、流程命名、设计模式 | 灰色，默认折叠，教师确认后转"确定" |
| **无依据（dropped）** | 没有证据支撑的 | 关键词贴标签出来的"设计思路" | **直接不展示** |

**为什么这个设计能换来信任：**
教师看到"这条是**推断**的，依据是这三行"会信任我们；看到一段流畅但没依据的"设计思路"会怀疑**全部**结论。
**诚实标注的可信度，比虚假的精确更能换来信任 —— 而这恰恰是我们相对大模型的优势，因为大模型没法给自己的每句话做自我标注。**

**需要改的代码位置：**
- [key_implementation.py](engine/deep_analyzer/key_implementation.py) —— 所有 `_infer_*` / `_match_*` / `_classify` 方法增加 `confidence` 字段与 `evidence_refs` 强制绑定
- [design_pattern_detector.py](engine/deep_analyzer/design_pattern_detector.py) —— 默认输出全部降级为 `unconfirmed`，除非能给出结构证据
- [deep_analysis.py](engine/deep_analyzer/deep_analysis.py) —— `to_dict()` 输出增加 `confidence` 字段，前端按等级渲染
- [frontend/](frontend/) —— 分析报告页增加可信度图例与筛选

### 痛点 3：评测的信任基础 —— 数据哪来？谁来判？AI 迎合怎么办？

这是最难的一环。**核心解法只有一句话：把"打分"和"判断"彻底拆开。**

评测分三层，**每层的判定主体不同**：

#### 第一层：可判定题（占题库 60-70%）—— 规则引擎判，不涉及 AI

凡是答案能还原成**代码事实**的题，答案唯一，用规则引擎判，**确定性 100%，跟 AI 的判断力毫无关系**：

| 题型 | 答案来源 | 引擎模块 |
|------|---------|---------|
| 流程排序题 | 调用图 BFS 顺序 | [project_call_graph.py](engine/deep_analyzer/project_call_graph.py) |
| 模块归属题 | 模块聚类结果 | [module_analyzer.py](engine/project_analyzer/module_analyzer.py) |
| 条件判断题 | AST 的 If / BoolOp 条件单 | [key_implementation.py](engine/deep_analyzer/key_implementation.py) |
| 状态变更题 | 属性读写检测 | [state_tracker.py](engine/deep_analyzer/state_tracker.py) |

**这一层回答了"数据哪来"：数据来自代码本身，不来自 AI。** 判分是集合比对，不是语义判断。

#### 第二层：语义理解题（20-30%）—— AI 出题，**教师审答案**

"这个模块为什么这样拆""这个流程的设计意图是什么"。
AI 可以出题、可以起草参考答案，但 **答案必须经教师确认才入答案库**。

> **题可以 AI 出，答案必须有人背书。** 责任人从 AI 转回教师，教师才敢用。

#### 第三层：开放题 —— **不给分，只给覆盖度报告**

**这一层直接解决"豆包一直迎合你"的问题。**

做法：**不要让 AI 判断"对不对"，让 AI 抽取"提到了哪些事实"，然后跟事实表做比对。**

```
事实表（规则引擎产出，教师可审可改）
  F1  冲突检测发生在写入之前          reservation_manager.py:88
  F2  自己预约自己被拒绝              reservation_manager.py:76
  F3  取消时释放时段                  reservation_manager.py:134
  F4  跨天预约的处理方式              reservation_manager.py:95
  F5  并发下的竞态处理                （未实现 —— 明确告诉学生"该场景代码里没有"）

学生自由作答
  ↓
AI 只做一件事：把答案映射到 F1-F5 的覆盖情况
  ↓
覆盖报告
  F1 ✅   F2 ❌   F3 ✅   F4 未提及   F5 未实现
  → 覆盖 2/4，缺 F2、F4，建议回看 reservation_manager.py:76
```

**为什么这样设计 AI 就无法迎合：**

- AI 不再判断对错，只做"这句话在讲哪个事实 id"的**抽取**工作
- 抽错了是映射错误，不是编造；错误的可观测性完全不同
- 必须给模型一个**"无法确定"选项**，并在提示词里明确写：
  > "如果你无法判断学生的话对应哪个事实，必须输出 `unknown`。
  >  **不允许为了让学生感觉良好而给出正向判定。** 该场景的评分容错由教师承担，不由你承担。"
- **覆盖度是可核验的，分数不是。**

#### 信任基础的三根支柱

信任不来自"我们的 AI 很准"，来自：

1. **答案可复现** —— 同一份代码跑两次，答案集完全一致（规则引擎保证）
2. **答案可追溯** —— 学生点一下就能看到行号证据
3. **教师有一票否决权** —— 教师改过的答案，下次生成不许被覆盖

**第 3 点目前完全没有实现，但它恰恰是最能打动教师的功能。**

## 四、业务逻辑生成的可靠性：现状盘点与改造步骤

### 4.1 现状分级（诚实版）

| 组件 | 文件 | 可靠性 | 说明 |
|------|------|--------|------|
| AST 基础解析 | [python_parser.py](engine/parser/python_parser.py) | **确定** | 类/函数/行号/import，无争议 |
| 项目级调用图 | [project_call_graph.py](engine/deep_analyzer/project_call_graph.py) | **确定** | 跨文件调用解析，可复核 |
| 状态读写追踪 | [state_tracker.py](engine/deep_analyzer/state_tracker.py) | **确定** | 属性读写检测，可复核 |
| 依赖强度 | [dependency_strength.py](engine/deep_analyzer/dependency_strength.py) | **确定** | 基于真实调用次数统计 |
| 模块架构分层 | [module_architecture.py](engine/deep_analyzer/module_architecture.py) | **推断** | 分层规则有效，但边界需人看 |
| 业务流程提取 | [flow_extractor.py](engine/deep_analyzer/flow_extractor.py) | **推断** | BFS 链路确定，但"入口点"识别靠启发式 |
| 关键实现解析 | [key_implementation.py](engine/deep_analyzer/key_implementation.py) | **部分不可用** | 结构指标确定，但 `_infer_design_approach` / `_infer_algorithm_type` 是关键词贴标签 |
| 设计模式识别 | [design_pattern_detector.py](engine/deep_analyzer/design_pattern_detector.py) | **误报高** | 1037 行，结构猜测，误报率未实测 |
| 训练题生成 | [training_generator.py](engine/project_analyzer/training_generator.py) | **需改造** | 模块归属/排序题可用，实现思路题依赖上面的推断 |

**这张表应该成为项目对外材料的核心附件。** 敢把自己引擎的可靠性分级公开，本身就是最强的信任信号。

### 4.2 改造步骤（按顺序执行，每步有验收标准）

#### Step 1（1-2 天）：给数据结构加可信度字段

- 在 `KeyImplementation`、`ModuleInfo`、`BusinessFlow`、`DesignPattern` 等 dataclass 增加 `confidence: str`（`verified` / `inferred` / `unconfirmed`）
- `to_dict()` 同步输出
- **验收：任意一条分析结论，都能在 JSON 里看到它的可信度等级**

#### Step 2（2-3 天）：把关键词贴标签降级或删除

- 删除 `_infer_algorithm_type` 中所有纯名字匹配的分支（如 `if "conflict" in name_lower`）
- 改造 `_infer_design_approach`：**每条描述必须绑定至少一条 `evidence_ref`**，绑定不上就不输出
- **验收：随机抽 20 条结论，每条都能点开看到支撑它的代码行；做不到的那条直接不输出**

#### Step 3（3-5 天）：设计模式识别降级

- `design_pattern_detector` 的所有输出默认为 `unconfirmed`
- 只有能给出**结构证据**的（如"实现了同一接口的 N 个类 + 运行时按 key 选择"→ 策略模式）才升为 `inferred`
- 在 UI 上折叠展示，标注"待教师确认"
- **验收：教师看到设计模式结论时，第一反应不是"这也算？"**

#### Step 4（5-10 天）：教师审核与固化

- 分析结果增加"编辑"与"确认"操作
- 确认后的结论存入独立层，**重新生成分析时优先使用教师版本，不被覆盖**
- 记录修改人、修改时间、修改原因
- **验收：教师改一条 → 重新跑分析 → 修改还在**

#### Step 5（3-5 天）：前端可信度渲染

- 分析报告页增加图例：绿=确定 / 黄=推断 / 灰=待确认
- 支持按可信度筛选
- 推断类结论展开显示依据行
- **验收：教师扫一眼就能分清哪些能直接用、哪些要先看一眼**

## 五、评测改造步骤（对应痛点 3）

#### Step A（2-3 天）：建立事实表提取器

- 新增模块：从规则引擎结果中抽取"事实条目"，每条含 `id / 描述 / filepath / line / confidence`
- 事实表是**可导出、可审核、可版本化**的独立产物
- **验收：导出的事实表能被教师直接 Excel 打开核对**

#### Step B（2 天）：题库分层

- 现有题目标注为 `deterministic`（可判定）或 `semantic`（语义）
- 可判定题走纯规则判分，**完全不调 LLM**
- **验收：可判定题在不联网的环境下也能出题、判分**

#### Step C（3-4 天）：覆盖度评分器

- 输入：学生自由作答 + 事实表
- 输出：`{covered: [F1,F3], missed: [F2,F4], unknown: [], not_implemented: [F5]}`
- 提示词中强制包含"无法确定"出口与"禁止迎合"约束
- **验收：同一份答案连续跑 10 次，覆盖判定结果一致；教师能一眼看出 AI 没有瞎给分**

#### Step D（2-3 天）：答案库与教师背书

- 语义题的参考答案只有教师确认后才进入答案库
- 未确认的语义题**不允许出现在正式作业里**
- **验收：教师能明确看到"这道题的答案我还没确认过"**

## 九、市场与场景

### 9.1 谁付钱

在中国高校，**单个教师为"备课工具"付费极其困难**。真正的采购单元是**系 / 教研室 / 课程组**。

**采购动机不是"帮你省时间"，而是：**
- 教改项目申报材料
- 一流课程申报佐证
- 工程教育认证（OBE）的课程目标达成度证据

**这意味着"证据链"和"覆盖度报告"不只是技术方案，它们就是采购理由** ——
认证评审要看的正是"课程目标达成度证据链"。我们已经在做证据链了，
**把它包装成"达成度分析报告"，卖点完全不同。**

### 9.2 三个使用场景

| 场景 | 用户 | 核心价值 | 状态 |
|------|------|---------|------|
| **教师备课** | 教师 | 上传项目 → 生成全套教学材料 | 优先级最高 |
| **学生自学** | 学生 | 引导式四关训练 | 依赖评测改造完成 |
| **作业测评** | 教师 + 学生 | 覆盖度报告 + 班级看板 | 依赖 [第五步](#五评测改造步骤对应痛点-3) |

### 9.3 一个更大的机会：项目案例库

教师用完分析功能后，**下一个需求一定是"帮我挑个项目"**。

> ⚠️ **项目不能靠 AI 现场生成。** AI 生成的项目在工程上往往不成立 —— 跑不通、没有真实复杂度、没有真实的业务约束。**这个坑千万别踩。**

正确做法：**把已分析过的项目沉淀成可检索的案例库** ——
按知识点、难度、技术栈、规模、架构风格索引。教师输入"我要讲观察者模式和事务边界，Java，大二水平"，
返回若干候选项目 + 现成的三层拆解 + 现成的题目。

**当库里有 200 个真实项目时，"项目案例库"本身就能独立售卖，而且比"又一个 AI 代码解释器"值钱得多。**

## 十、设计哲学

### 为什么"可复现"是底线，而不是"更准确"

大模型可以讲得头头是道，但它说的不一定对，而且**每次说的都不一样**。

在教育场景里，有两件事比流畅性重要得多：

1. **同一份代码，同一个问题，答案必须稳定。** 否则教师无法备课，学生无法复习。
2. **每一条关于代码的事实性判断，必须能回指到行号。** 说"这个模块负责预约管理"不算数，必须能指出是哪些类、哪些方法、哪些代码行。

**证据链的三个好处：**
1. 学生可以追溯，知道结论是怎么来的
2. 教师可以审核，确保教学内容准确
3. **不依赖大模型也能运行核心功能，私有化部署无压力**

### 为什么坚持三层分析结构

人类理解复杂系统的规律是：**先看全貌，再抓核心，最后深入细节。**

- 第一层回答"这个项目长什么样" —— 建立全局认知
- 第二层回答"这个项目在干什么" —— 抓住业务主线
- 第三层回答"核心功能怎么做的" —— 深入设计和实现

跳过任何一层，理解都是不完整的。

### 规则引擎与 LLM 的分工

> **规则引擎做事实，LLM 做润色。**
> 确定性的结论全部来自静态分析；自然语言描述和引导语才交给 LLM。

**关于 LLM 接入的原则：不急着上。** 等规则引擎能提取的"事实"足够丰富了，再接 LLM 做语义层增强。
这样成本极低，并且**所有事实都可追溯、可审核**。

**特别是评测环节：凡是能判断对错的地方，一律不调 LLM。** 只有开放题才用 LLM，且只用它做事实覆盖度抽取。

## 十一、核心能力：三层业务逻辑分析

### 第一层：结构化拆解 — 这个项目长什么样

- **模块划分**：按职责聚类，识别每个模块的核心类和方法
- **职责定义**：每个模块做什么、不做什么，输入输出是什么
- **依赖关系**：模块之间谁调用谁，依赖强度有多大
- **架构分层**：自动识别编排层 / 业务层 / 支撑层
- **核心度排名**：哪些模块是核心，哪些是周边

**输出**：模块架构分层图 + 模块职责清单 + 依赖关系图

### 第二层：核心功能提取 — 这个项目在干什么

- **核心业务流程**：从入口点出发的完整调用链，标注跨模块跳转、状态变更、校验点
- **关键功能点**：项目最核心的 N 个功能，以及每个功能的业务含义
- **状态流转链路**：哪些操作改变了哪些状态，状态怎么迁移
- **按重要性排序**：核心的放前面

**每条结论都有证据**：哪个方法、哪个文件、哪一行代码，点过去就能看。

**输出**：业务流程时间线 + 核心功能清单 + 状态流转图

### 第三层：推荐实现思路 — 核心功能怎么做的

**⚠️ 当前可靠性最薄弱的一层，改造计划见 [4.2](#42-改造步骤按顺序执行每步有验收标准)。**

对每个核心功能提取：

- **实现思路**：整体设计思路（**必须有证据支撑，否则不输出**）
- **关键代码**：核心逻辑在哪些方法里，关键判断点在哪
- **边界条件**：处理了哪些异常、空值、并发、冲突检测
- **设计模式**：识别到的模式（默认"待确认"）
- **扩展点**：如果要加功能，应该从哪入手

**输出**：核心功能解析卡片 + 代码证据跳转 + 设计思路说明

### 分析引擎设计原则

1. **项目级而非函数级** —— 最小分析单元是完整模块 / 项目
2. **规则做骨架，事实可追溯** —— 所有结论有行号级证据
3. **从宏观到微观** —— 架构 → 模块 → 流程 → 实现
4. **LLM 增强但不依赖** —— 静态分析做事实层，LLM 做语义润色
5. **教师可审核可编辑** —— 分析结果不是黑盒
6. **诚实标注可信度** —— 推断的标推断，没依据的不输出
