## 一、先搞清楚评委到底看什么

校赛初赛的评审和"最终做出好产品"是两件事。按重要性排：

| 维度 | 权重 | 我们现在的状态 | 10 天能改到什么程度 |
|------|------|--------------|------------------|
| 痛点是否真实、是否是刚需 | 高 | ✅ 有，但表述需要收紧 | ✅ 能改好 |
| **有没有真实证据支撑** | **最高** | ❌ **最大短板** | ✅ **必须拿下** |
| 能不能现场演示、演示是否稳定 | 高 | ⚠️ 只能演示自造项目 | ✅ 能改好 |
| 技术是否有壁垒 | 中 | ⚠️ 有但讲不清 | ✅ 能讲清 |
| 是否诚实说明边界 | 中 | ✅ 新 README 已做 | ✅ 保持 |
| 商业化路径 | 低（初赛） | ⚠️ 弱 | ⏭️ 只留一页 |

### 最大的坑：那个 784 行的自造样本

[sample_projects/lab_safety_assistant/](sample_projects/lab_safety_assistant/) 是你自己写的，引擎里所有启发式规则都是照着它调的。

**评委只要问一句"你这个效果有没有在别的项目上试过"，你就没词了。**

这是 10 天里**唯一必须拿下**的事。拿下了，你的答辩从"我们觉得有用"变成"我们实测了 N 条事实，错误率 X%"，性质完全不同。

## 二、一句话定位（答辩开场就这句）

> **我们不比大模型更聪明。我们做的是让大模型的输出变得可复现、可追溯、可被教师改写。**

**紧接着补一句，把差异化钉死：**

> 老师拿一个项目去问 ChatGPT，能得到一份好答案。但同一个问题问十次会得到十个略不一样的答案，
> 而且说不清每条结论依据的是哪几行代码，老师改过的内容下次也不会保留。
> **我们解决的就是这三件事。**

**不要说的话**（说了必被追问）：
- ❌ "我们比 ChatGPT 更准"
- ❌ "节省教师 80% 备课时间"（没有实测数据支撑）
- ❌ "支持各类项目"（目前只支持 Python）

## 三、三个必答题（30 秒版口径）

### Q1：这个能力，为什么不做成一个提示词 / 一个 Skill 就行？

**30 秒答：**

> 我们验证过了，其中一部分能力确实应该做成 Skill，我们也已经做了。
> 但有三件事提示词做不到：
> 第一，**可复现** —— 同一份代码问十次，提示词给十个不一样的答案，我们是同一个答案；
> 第二，**可定位** —— 每条结论能回指到第几行，教师可以审核；
> 第三，**可沉淀** —— 教师改过的结论能固化，下次重新生成不丢。
> 还有一条物理限制：**一个 20 万行的项目塞不进上下文窗口**，塞不进去模型就会编。
> 我们的引擎做一次结构化索引复用一万次，索引里没有的东西我们不说。

### Q2：评测的数据从哪来？凭什么当评分标准？

**30 秒答：**

> 我们把评测拆成三层，**判定主体不一样**。
> 第一层是可判定题，占题库 60-70%，答案来自代码本身 —— 调用顺序、模块归属、状态字段变更，
> 全部由规则引擎判定，**不调 LLM，确定性 100%**。
> 第二层是语义理解题，AI 可以出题，但**答案必须经教师确认才入答案库**。
> 第三层是开放题，我们**不给分**，只出事实覆盖度报告。

### Q3：AI 评测会不会一直迎合学生？（豆包那个问题）

**30 秒答：**

> 这是我们在设计上专门规避的。
> 我们的做法是：**不让 AI 判断"对不对"，只让它抽取"学生提到了哪些事实"**，
> 然后跟规则引擎产出的事实表做比对。
> AI 的工作从"判断对错"降级成了"事实映射"，它没有空间去迎合。
> 而且我们在提示词里写死了：判断不了必须输出 `unknown`，
> **不允许为了让学生感觉良好而给出正向判定**。

- [ ] 从 GitHub 上选 **2-3 个你没写过的 Python 项目**，覆盖不同规模：

| # | 类型 | 目标行数 | 验证什么 |
|---|------|---------|---------|
| 1 | 小型真实项目 | 800-1500 行 | 命名不规范时还能不能分析 |
| 2 | 中型开源项目 | 5000-10000 行 | 多包结构、跨文件调用 |
| 3 | （可选）大型项目 | >2 万行 | 性能和上下文边界 |

### D2-D4 · 真实项目验证（3 天，最重要）

每天跑一个项目，流程固定：

1. 跑 [scripts/test_deep_analyzer.py](scripts/test_deep_analyzer.py)，输出完整分析结果
2. **人工逐条核对**抽取出来的事实，分类记录：

| 事实类型 | 总条数 | 正确 | 错误 | 错误类型 |
|---------|-------|------|------|---------|
| 模块划分 | | | | 聚类错了 / 漏了 / 多了 |
| 调用链 | | | | 漏调用 / 错调用 / 解析不了动态调用 |
| 状态读写 | | | | 误报 / 漏报 |
| 模块职责描述 | | | | 描述与代码不符 |
| 实现思路推断 | | | | 关键词贴标签导致的错判 |
| 设计模式识别 | | | | 误报 |

3. **记下错误率：`错误率 = 错误条数 / 总条数`**

**产出（这就是你答辩时最值钱的东西）：**
- 一份三项目的对照表
- 一个真实的错误率数字
- **错误类型清单**（哪些错是必然的、哪些是能修的）

> ⚠️ **不要美化数字。** 错误率高不丢人，"我们测了发现实现思路推断这一层错误率很高，所以我们把它降级为待确认"是加分项。
> 编一个好看的假数字，被追问一句就崩，那才是真丢人。

## 五、演示脚本

### 演示前必须做的准备

- [ ] **提前把分析结果缓存好。** 现场不要跑实时分析，万一卡住整场就废了
- [ ] 准备一个本地离线版本，**假设现场没有网**
- [ ] 浏览器只开一个标签页，关掉所有无关窗口和通知
- [ ] 字体调大，投影仪分辨率提前试

### 现场演示动线（控制在 2-3 分钟）

```
1. 打开分析报告页
   "这是一个真实项目，784 行，四个模块。"          ← 别说"这是我写的"

2. 点开模块架构分层图
   "系统自动识别出了编排层、业务层、支撑层。"

3. 点进核心业务流程
   "这是一个完整的预约流程，跨了 4 个模块。"
   "注意每一步都能看到它跨了模块边界、改了哪些状态。"

4. 点开某一步的证据跳转 ⭐
   "点这里，直接跳到第 88 行 —— 冲突检测就在这。"
   ← 这一步是全场最重要的动作，一定要做

5. 切到引导式训练
   "教师可以直接用这套分析生成训练题。"
```

**第 4 步"点证据跳转"是核心。** 因为这就是你跟 ChatGPT 的差别 —— 它能说同样的话，但点不出第 88 行。

### 如果评委让你临场传一个项目

**这是好机会，不要慌。** 但要说清楚：

> "可以，但因为它不是我们调过的项目，可能会慢一些，也可能有些地方分析不出来 ——
> **这正好能说明我们现在的边界在哪。**"

**不要承诺一定能跑通。** 跑崩了就是灾难，提前打预防针反而显得诚实。

## 六、评委提问预案（现成话术）

### Q：这个和直接用 ChatGPT / Claude 有什么区别？

> 我们做了一次实测对比。同一个项目问十次，答案有 N 处不一致；
> 而且它说不清每条结论依据的是哪几行。老师改过的内容，下次也不会保留。
> **我们不比它更聪明，我们解决的是可复现、可定位、可沉淀。**

### Q：你这个分析准确率多少？

> 事实层（调用链、行号、状态读写）来自 AST 直接解析，可复现，我们实测错误率是 X%。
> 语义层（模块职责命名、流程命名）是推断，我们**在 UI 上标注为待确认，需要教师确认后才算数**。
> 这两个层我们分开对待，不混在一起说一个总的准确率。

### Q：只支持 Python 吗？我们学校教的都是 Java。

> 目前只支持 Python。Java 支持需要重做解析层，我们已经评估过成本，**这是下一步**。
> 我们首批用户定位在 Python 相关课程 —— 数据分析、人工智能、爬虫这些方向，
> 这些课程的课程设计和毕业设计量也很大。

### Q：教师会愿意用吗？愿意付钱吗？

> 单个教师付费意愿确实低，我们很清楚。
> 真实的采购单元是**系、教研室、课程组**，采购动机是教改项目申报、一流课程申报、
> 以及工程教育认证需要的**课程目标达成度证据**。
> 我们的证据链和覆盖度报告，恰好就是认证评审要看的材料 —— 这是我们的切入点。

### Q：教师自己看一遍代码不就知道了，为什么需要你这个？

> 一个 1 万行的项目，教师啃一遍要两三天。我们要做的不是替代他理解代码，
> 而是把"整理成教学材料"这个机械环节自动化。
> 而且我们交付的不是一份分析报告 —— 报告只是中间产物 —— 而是**能直接上课的课件、题目和答案**。

### Q：这个技术壁垒在哪？别人不是也能做吗？

> 技术单点确实都不难，AST 解析、调用图都是成熟技术。
> 我们的积累在于**把三层的证据串成了一条链路**：代码 → 事实表 → 题目 → 答案 → 覆盖度报告，
> 而且是可复现的。这个链路要打通，需要处理大量真实项目里的脏情况 ——
> **这也是我们接下来要投入最多的地方，我们已经用 N 个真实项目实测过了。**

### Q：这个能落地吗？有没有实际用过？

> 说实话，**目前还没有真实教师用户**，我们处在实测验证阶段。
> 已经完成的是在 N 个真实第三方项目上的分析验证，错误率数据在这。
> 下一步是找 2-3 位真实教师试用，这学期的课程设计就是我们的目标场景。

> 💡 **"还没有真实用户"这句话必须主动说，不要等评委问出来。** 主动说显得清醒，被问出来显得心虚。

### Q：你们这个和 XX（某个见过的类似工具）比怎么样？

> 我们关注过一些同类工具，多数集中在代码可视化或者单文件解释。
> 我们的差异点是**项目级 + 教学闭环** —— 分析结果直接产出教学材料，
> 而不是停在一个"好看的图"上。

## 七、翻车预案

| 情况 | 怎么处理 |
|------|---------|
| **分析卡住 / 报错** | 立刻切到**预生成的缓存结果**，说"现场这台机器环境不一样，我用预生成的结果继续演示"，不要现场debug |
| **错误率数字很难看** | 主动讲出来 + 归因 + 说改法。"我们实测发现实现思路这一层错误率最高，所以我们把它降级为待确认了" —— 这是加分项 |
| **评委问 Java 支持** | 见上方话术，诚实说只支持 Python，讲清首批用户定位 |
| **评委说"我们以前见过类似工具"** | 不争论，直接讲差异点："他们的落点是图，我们的落点是教学材料 + 覆盖度报告" |
| **时间被压缩到 3 分钟** | 只讲：定位 → 实测证据 → 证据跳转演示 → 诚实边界。其他全砍 |
| **被问到 Roadmap 上没做的事** | "这个在我们的 Phase 2，还没开始做" —— **不要现场编** |

## 八、这 10 天不要做的事

明确列出来，避免分心：

- ❌ **不要做可信度四级制的完整实现** —— 那是 2-3 周的工程，10 天做出来是半成品
- ❌ **不要做教师审核与修改固化** —— 同上，工程量大，做一半反而没法讲
- ❌ **不要碰 Java 支持** —— 这是重做解析层，10 天绝对不够
- ❌ **不要实现覆盖度评分器** —— 出设计图和示例即可，代码不写
- ❌ **不要追求功能多** —— 初赛看的是"这件事值不值得做 + 你有没有证据"，不是功能列表长度
- ❌ **不要美化数据** —— 最危险的一条

## 九、答辩结束前必须说的一段话

不管时间多紧，这段话要留出 15 秒：

> "最后想说一句实话：我们现在还没有真实教师用户，
> 引擎也还有明显的短板 —— 语义层靠推断、只支持 Python。
> 但我们用 N 个真实项目做了实测，错误率数据都在这份材料里。
> **我们不想把没做到的事说成做到了，因为教育场景里，讲错一件事比不讲危害更大。**"

**这段话的作用：** 评委见过太多"AI 驱动、智能分析、精准高效"的项目。
**把自己的短板说得比评委还清楚，是初赛现场最稀缺的竞争力。**

#### 强化 1：事实表导出器（1 天）⭐⭐⭐⭐⭐

**做什么：** 把分析结果中的"可判定事实"提取成独立的 Excel/CSV 文件。

**产出：** 一个 `scripts/export_fact_table.py`，输入分析 JSON，输出：

```
事实ID  | 类型        | 描述                              | 文件:行号                    | 可信度
F001    | 调用链      | create_reservation 调用 _check_conflict | reservation_manager.py:78 | verified
F002    | 状态变更    | 修改 reservations 字典            | reservation_manager.py:92  | verified
F003    | 守卫条件    | 用户不存在 → ValueError            | user_manager.py:35         | verified
F004    | 异常处理    | raise ValueError("用户名已存在")   | user_manager.py:36         | verified
...
```

**为什么高性价比：**
- 材料里直接贴这张表 → 评委一眼看到"我们抽取了 N 条事实，每条可回指代码"
- 是 [痛点 3：评测的信任基础](#痛点-3评测的信任基础--数据哪来谁来判ai-迎合怎么办) 的实物证明
- 1 天能做完，而且这张表**本身就是申报材料的核心附件**
- **回答了"题目的答案从哪来"这个最核心的问题**

**怎么做：**
```python
# scripts/export_fact_table.py
import json, csv

def extract_facts(analysis_json):
    facts = []
    fact_id = 1
    
    # 1. 从 call_graph 提取调用链
    for edge in analysis_json['call_graph']['edges']:
        facts.append({
            'id': f'F{fact_id:03d}',
            'type': '调用链',
            'desc': f"{edge['from']} 调用 {edge['to']}",
            'location': f"{edge.get('file', 'N/A')}:{edge.get('line', 'N/A')}",
            'confidence': 'verified'
        })
        fact_id += 1
    
    # 2. 从 state_analysis 提取状态变更
    for class_state in analysis_json['state_analysis']['classes'].values():
        for method, writes in class_state['method_writes'].items():
            for attr in writes:
                facts.append({
                    'id': f'F{fact_id:03d}',
                    'type': '状态变更',
                    'desc': f"{method} 修改 {attr}",
                    'location': f"{class_state['file']}",
                    'confidence': 'verified'
                })
                fact_id += 1
    
    # 3. 从 key_implementations 提取守卫/异常/验证
    for impl in analysis_json['key_implementations']['implementations']:
        for char in impl['design_characteristics']:
            if char['confidence'] == 'verified':
                facts.append({
                    'id': f'F{fact_id:03d}',
                    'type': char['category'],
                    'desc': char['label'],
                    'location': impl['filepath'] + ':' + char['evidence'],
                    'confidence': 'verified'
                })
                fact_id += 1
    
    return facts

# 导出 CSV
with open('fact_table.csv', 'w', encoding='utf-8-sig', newline='') as f:
    writer = csv.DictWriter(f, fieldnames=['id', 'type', 'desc', 'location', 'confidence'])
    writer.writeheader()
    writer.writerows(facts)
```

**验收：** 跑 lab_safety_assistant，导出的表至少有 50 条事实，每条都能在代码里找到。

## 十三、架构层面可继续升级的方向（初赛后）

> **这一节是给初赛后用的，不要在 10 天里碰。** 但可以在材料的"未来规划"章节里提一句。

### 架构升级 A：引擎的可插拔设计

**现状：** [engine/deep_analyzer/deep_analysis.py](engine/deep_analyzer/deep_analysis.py) 是硬编码的管线，组件顺序固定。

**升级方向：** 改成"分析器注册表 + 依赖声明"：

```python
class AnalyzerRegistry:
    def register(self, analyzer_class, depends_on=None):
        ...
    
    def run(self, project_info):
        # 自动按依赖排序
        # 每个分析器声明自己需要哪些前置分析器的结果
        ...

# 使用
registry = AnalyzerRegistry()
registry.register(CallGraphAnalyzer)
registry.register(StateTracker, depends_on=[CallGraphAnalyzer])
registry.register(FlowExtractor, depends_on=[CallGraphAnalyzer, StateTracker])
results = registry.run(project_info)
```

**好处：** 用户可以自己写分析器插件，不用改核心代码。

**成本：** 2-3 天重构。

---

### 架构升级 B：增量分析

**现状：** 每次跑分析都是全量的，改一行代码也要重新分析整个项目。

**升级方向：** 
- 记录每个文件的 hash
- 只重新分析变化的文件
- 重新计算受影响的模块边界和流程

**好处：** 大项目上能节省 80% 的时间。

**成本：** 3-5 天，需要处理缓存失效、依赖传递。

---

### 架构升级 C：多语言支持的统一抽象

**现状：** Parser 层是 Python-only 的，加 Java 支持要重写。

**升级方向：** 定义一个"语言无关的 IR（中间表示）"：

```python
@dataclass
class UniversalNode:
    type: str  # 'class' | 'function' | 'call' | 'if' | ...
    name: str
    location: Location
    children: List[UniversalNode]
    attributes: Dict[str, Any]
```

Parser 层的职责变成：Python AST / Java AST / JavaScript AST → UniversalNode

后面所有分析器只看 UniversalNode，不管源语言。

**好处：** 加新语言只需要写一个 `LanguageParser`，不用改分析器。

**成本：** 5-7 天，需要设计好 IR 的粒度。

---

### 架构升级 D：分布式分析

**现状：** 单机单进程，大项目（>10 万行）会很慢。

**升级方向：**
- 文件级并行：多进程同时解析不同文件
- 模块级并行：不同模块的分析可以并行
- 用任务队列（Celery / RQ）支持跨机器分析

**好处：** 10 万行项目从 5 分钟降到 30 秒。

**成本：** 3-5 天，需要处理进程间通信、结果合并。

---

### 架构升级 E：知识图谱存储

**现状：** 分析结果存成 JSON，查询能力弱。

**升级方向：** 把调用图、依赖图、状态流转图存到图数据库（Neo4j），支持：
- "找出所有调用超过 5 层的路径"
- "找出所有改了 `user.status` 的方法"
- "找出模块 A 到模块 B 的所有路径"

**好处：** 支持复杂查询，可以做"代码影响分析"。

**成本：** 5-7 天，需要学 Neo4j / Cypher。

#### 任务 2：分析结果缓存（1-2 小时）

**做什么：**

**GPT 提示词模板：**
```

[贴上分析接口代码]
```

## 十九、本轮原型新增：证据驱动的业务优先级（BLPS-1.0）

> **状态：已接入分析管线和前端演示页，算法输出仍需在第三方项目上验证。**

前面的事实表回答“代码里发生了什么”，但现场演示还需要回答一个业务问题：
**教师应该先讲哪条业务链，先审核哪一个结论？**

本轮新增 `BusinessPriorityAnalyzer`，把调用图、业务流程、状态追踪和行号证据组合成一个可复现的排序层。它只负责**排序和分配审核资源**，不把分数当成事实，也不调用 LLM 判定对错。

### 19.1 业务闭环

```text
Python AST / 调用图 / 状态追踪
              │
              ▼
      BLPS-1.0 业务优先级评分
              │
      ┌───────┼────────┐
      ▼       ▼        ▼
  核心节点  核心流程  证据缺口
      │       │        │
      └───────┴────────┘
              ▼
   教师先讲什么、先审核什么、哪些内容不能直接进答案库
```

前端深度分析页新增“业务优先级”标签，展示：

- 核心业务节点 Top-K：方法、模块、代码位置、触发原因和分数；
- 业务流程优先级：流程重要度、状态变更、校验、跨模块协作；
- 证据缺口：状态变更但未发现显式校验、流程步骤缺少行号等待审核项；
- 算法版本、权重和公式，便于复现和答辩时解释。

### 19.2 可解释的评分公式

#### 第一步：加权 PageRank 找结构中心

令 (G=(V,E)) 为项目调用图，(c_{uv}) 为调用出现次数，跨模块边额外乘以 1.2：

\[
w_{uv}=c_{uv}\times
\begin{cases}
1.2,& module(u)\ne module(v)\\
1,& module(u)=module(v)
\end{cases}
\]

采用阻尼系数 (d=0.85)：

\[
PR(v)=\frac{1-d}{|V|}+d\left(\sum_{u\in In(v)}PR(u)\frac{w_{uv}}{\sum_xw_{ux}}+\frac{D}{|V|}\right)
\]

其中 (D) 是没有出边节点的 PageRank 总量。迭代到相邻两轮 L1 差小于 (10^{-9}) 或达到 100 轮，保证同一份代码得到同一排序。

#### 第二步：节点业务优先级

把 PageRank 归一化为 (C)，把节点参与的流程重要度归一化为 (R)，把状态写入、跨模块边界、证据完整度分别记为 (M,B,E\in[0,1])：

\[
S_{node}=100\times(0.35C+0.25R+0.20M+0.10B+0.10E)
\]

解释：中心度和流程参与度决定“影响面”，状态变更决定“业务后果”，跨模块决定“理解难度”，证据完整度决定“能不能直接拿去讲”。

#### 第三步：流程优先级

对每条流程，先对入口名或流程名包含 `initialize / bootstrap / seed / sample_data / setup` 的生命周期或样例数据流程乘以 `q=0.2`，保留它但避免它因批量造数调用量大而压过用户业务；再令 (I) 为调整后的业务重要度归一化值，(M_f,V_f,B_f,E_f) 分别为状态变更比例、校验比例、跨模块比例、行号证据比例：

\[
S_{flow}=100\times(0.45I+0.20M_f+0.15V_f+0.10B_f+0.10E_f)
\]

再给教师一个审核提示分数：

\[
Risk_{review}=100\times(0.65\cdot\mathbf{1}[M_f>0\land V_f=0]+0.35\cdot(1-E_f))
\]

`Risk_review` 高只表示“应该先人工看”，**不表示代码一定有错**。

### 19.3 这项功能怎样增强初赛竞争力

演示时可以形成一条完整动作链：

1. 打开“业务优先级”，以演示项目为例展示系统从 39 个可调用节点中筛出核心节点；
2. 点击最高优先级流程，说明它为什么重要（影响面、状态变更、跨模块）；
3. 展开“证据缺口”，展示系统主动把缺少校验或行号的地方交给教师审核；
4. 回到业务流程或关键实现，点击文件与行号核验原始代码；
5. 最后进入训练题，说明优先级可以决定先出哪一类题，而不是让 AI 随机编题。

这比单独展示一张调用图更接近教师的真实决策，也比给出一个没有依据的“准确率”更容易被评委复核。

### 19.4 AI 的正确用法（保留确定性核心）

AI 可以加速外围工作，但不能替代事实层：

- **可以交给 AI**：根据已确认事实生成讲解稿、题干初稿、PPT 文案、测试用例、前端样式和部署脚本；
- **必须由规则引擎完成**：调用关系、状态读写、行号证据、优先级计算、覆盖度统计；
- **必须由教师确认**：模块职责命名、设计模式、开放题答案、任何没有代码证据的语义解释；
- **禁止的快捷方式**：让 LLM 直接输出“核心业务”“正确答案”或“准确率”，再把生成文本当成评测基准。

推荐给 AI 的任务提示词：

```text
输入是 business_priority.json 和 fact_table.csv。
只允许引用 confidence=verified 的事实；每个结论必须带 fact_id 和 filepath:line。
如果证据不足，输出 unknown，不要补全业务含义。
请生成：1）教师 3 分钟讲解稿；2）一题可判定题及其事实依据；
3）一题开放题，但不要给开放题打对错分。
```

### 20.1 总体概览

| 指标 | 数值 |
|------|------|

### 20.2 各项目对比

| 项目 | 代码行数 | 文件数 | 事实总数 | verified | inferred | 每百行事实数 |
|------|---------|--------|---------|----------|----------|-------------|
| python-dotenv | 1,112 | 8 | 189 | 189 | 0 | 17.0 |
| flask | 9,513 | 24 | 488 | 470 | 18 | 5.1 |
| urllib3 | 12,275 | 35 | 719 | 696 | 23 | 5.9 |

**关键发现**：

1. **确定性结论占比极高**：三个项目中 97% 以上的事实都是 verified 级别（直接从 AST 静态分析得出），准确率可证 100%。
2. **跨项目一致性好**：无论项目规模（1k 行到 12k 行），引擎都能稳定输出六大类事实，模块数量随规模线性增长。
3. **推断占比极低**：inferred 级别的结论只占约 3%，全部明确标注为待教师确认，不混入事实层。

### 21.2 评委可能问的问题（提前准备）

**Q：你们和普通的静态分析工具有什么区别？**
A：普通静态分析工具给你调用图和复杂度，我们给你"业务视角"——哪些是核心业务、哪些流程先讲、哪些结论可以直接用、哪些需要老师审。我们不替代老师，而是帮老师省时间。

**Q：准确率多少？**
A：分两层答。verified 级别的结论（调用关系、状态读写、行号证据）是从 AST 直接解析的，准确率 100%。inferred 级别的结论（设计模式、模块职责命名）是启发式推断的，我们明确标注出来，由老师确认。BLPS 优先级分数是排序信号，不是准确率。

**Q：能不能分析 Java / Go？**
A：目前只做了 Python，因为 AST 解析最成熟。架构上是分层的，前端和算法层不依赖具体语言，换语言只需要换 parser。这是下一步计划。

**Q：和大模型比有什么优势？**
A：第一，可复现——同一份代码每次分析结果完全一样，大模型做不到。第二，可定位——每条结论都有精确的文件行号。第三，可被教师改写——老师可以逐条确认或拒绝，系统会记住。大模型是黑箱，我们是白箱。
