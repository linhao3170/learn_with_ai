## 一、我们真正要培养的是什么

不是「学生会不会看代码」，也不是「学生能不能答对几道题」，而是：

> 学生能不能把一个真实项目拆解成业务模块，理解每个模块为什么存在、负责什么、和其他模块如何协作，
> 并且能够**在新需求下自己重新设计出合理的模块结构**。

所以项目核心要从「代码分析器」升级成「业务逻辑建模训练系统」。
**代码分析只是证据来源，学生最终要获得的是业务逻辑思维。**

### 1.1 明确不是什么

> ❌ 不是学生刷题的做题平台
> ❌ 不是测代码能不能跑通的 OJ 系统
> ❌ 不是又一个 AI 代码解释器
> ❌ 不是「比 ChatGPT 分析得更准」的工具 —— **我们赢不了这条，也不该往这条上撞**
>
> ✅ 是一条从代码到题目到答案的**可追溯、可复现、可被教师改写**的证据链
> ✅ 是教师的**项目教学材料生成器**
> ✅ 是**业务逻辑思维培养平台**：从「看懂代码」到「自己会设计」

### 1.2 为什么这件事不能靠一个提示词解决

判断一个能力该不该做成平台，只有一条尺子：

> **如果一份提示词 + 一个脚本就能交付，它就不该是平台。**

按这条尺子量我们自己的功能：

| 能力 | 正确形态 | 理由 |
|---|---|---|
| 生成一份项目分析报告 | **Skill / CLI** | 一次性、无状态、不需要沉淀 |
| 教案导出 PPT / Word | **Skill** | 模板化输出，无跨会话状态 |
| 学生答题 + 数据回流 | **平台** | 需要跨人、跨时间、跨班级的状态 |
| 一个班 40 份作业的一致性批改 | **平台** | 必须共享同一份事实基线 |
| 教师审核界面 + 修改固化 | **平台** | 需要 UI 和持久化 |
| 项目案例库检索 | **平台** | 需要索引和复用 |

**结论：我们现在有一半的功能应该先做成 Skill。** 平台化不是目的，是 Skill 验证失败之后的必然结果。

但有四件事提示词做不到：

1. **可复现**——同样的代码问十次，提示词给十个不一样的答案，我们是同一个答案；
2. **可定位**——每条结论能回指到第几行，教师可以审核；
3. **可沉淀**——教师改过的结论能固化，下次重新生成不一；
4. **设计能力培养**——提示词能给你一份分析，但不能带着学生一步步从「看懂」走到「自己会设计」。

还有一条物理限制：**一个 20 万行的项目塞不进上下文窗口**，塞不进去模型就会编。
我们的引擎做一次结构化索引复用一万次，**索引里没有的东西我们不说**。

> ⚠️ **这件事必须实测，不能靠嘴说。**
> 待做的《Skill 失效点实测报告》要覆盖五个维度：一致性（同一问题问 10 次，逐处列出不一致）/
> 可定位性 / 大项目（>5 万行）/ 可改写（教师改一条后重新生成）/ 批量一致性（同一基线批改 40 份作业）。
> **如果实测下来纯 Prompt 全都做到了 —— 那就应该停掉这个项目，或者只做 Skill 版本。这是必须接受的结论。**

### 1.3 护城河：可复现、可定位、可沉淀

> 老师拿一个项目去问 ChatGPT，能得到一份不错的代码讲解。但同样的问题问十次，会得到十个略有不同的答案，
> 而且说不清楚每条结论依据的是哪几行代码。
>
> 我们解决的是三件事：**可复现、可定位、可沉淀**——但这只是基础。
> **真正的差异化是：我们不只让学生「看懂一个项目」，而是培养他们「为新需求设计合理模块结构」的能力。**

**所有对外表述都必须围绕这三件事展开，而不是围绕「准确率」。**

### 1.4 谁付钱、为什么买

- 单教师付费意愿低，我们很清楚；
- 真实采购单位是**系 / 教研室 / 课程组**；
- 采购动机是**教改项目申报、一流课程申报、工程教育认证（OBE）的课程目标达成度证据**。

> 同一个系统，包装成「达成度分析报告」，卖点完全不同。
> 认证评审要看的正是「课程目标达成度证据链」——我们已经在做证据链了。

### 1.5 一个更大的机会：项目案例库

教师用完分析功能后，**下一个需求一定是「帮我挑个项目」**。

> ⚠️ **项目不能靠 AI 现场生成。** AI 生成的项目在工程上往往不成立——跑不通、没有真实复杂度、
> 没有真实的业务约束。**这个坑千万别踩。**

正确做法：**把已分析过的项目沉淀成可检索的案例库**——按知识点、难度、技术栈、规模、架构风格索引。
**当库里有 200 个真实项目时，「项目案例库」本身就能独立售卖。**

## 二、双层图谱：业务图谱 + 代码证据图谱

整个系统围绕一张「双层图谱」运行：

```text
业务逻辑图谱（学生面向的第一张图）
项目
 ├── 一级业务模块（业务域）
 │    ├── 二级功能模块（能力点）
 │    │    ├── 具体动作（对应真实函数）
 │    │    ├── 业务规则（对应真实 if / raise）
 │    │    └── 状态变化（对应真实属性 / 字典写入）
 │    └── ...
 └── ...

代码实现图谱（证据，第二张图）
项目
 ├── 文件
 ├── 类
 ├── 函数
 ├── 调用关系
 ├── 条件分支
 └── 数据读写
```

两张图之间建立**双向映射**：

```text
实验室预约（二级功能模块）
  ├── 提交预约       → ReservationManager.create_reservation   reservation_manager.py:56-104
  ├── 冲突检测       → ReservationManager._check_conflict      reservation_manager.py:106-124
  ├── 审批处理       → ReservationManager.approve_reservation  reservation_manager.py:126-137
  └── 取消预约       → ReservationManager.cancel_reservation   reservation_manager.py:153-166
```

**学生主要学习第一张图，需要证据时再打开第二张图。**
这样可以避免学生一开始就陷入函数、变量和代码行——先建立业务结构，再理解技术实现。

### 2.1 铁律：结论必须分层标注

任何一条结论都要带置信度，**进学生视图的只有三档，没有第四档**：

| 置信度 | 含义 | 来源 | 学生界面 |
|---|---|---|---|
| `verified` | 可由 AST / 调用图 / 状态追踪 / 行号直接证实 | 规则引擎 | 可展示 |
| `inferred` | 由命名、注释、结构启发式推断 | 规则引擎 + 可解释依据 | 展示但标「系统推断」 |
| `unconfirmed` | 需要业务理解，规则引擎给不出 | 待教师审核 | 显示但标「待教师确认」（可配置隐藏） |
| （`dropped`） | **无证据支撑**的结论 | — | **直接不展示** |

> 历史上旧 README 用的是四级制（`verified` / `inferred` / `unconfirmed` / `dropped`）。
> 工程实现把「无依据」当作**不产出**处理（`engine/business_graph/facts.py` 只给代码表达式，
> 推不出业务含义就标 `verified_code_only`），所以对外只讲三档 + 一条「无依据不展示」的规则。

**为什么这个设计能换来信任：**
教师看到「这条是**推断**的，依据是这三行」会信任我们；看到一段流畅但没依据的「设计思路」会怀疑**全部**结论。
**诚实标注的可信度，比虚假的精确更能换来信任——而这恰恰是我们相对大模型的优势，
因为大模型没法给自己的每句话做自我标注。**

### 2.2 铁律：无证据不入学生视图

1. 每条解释至少绑定一条 `Evidence`（`fact_id` + `file` + `start_line` + `end_line`）；
2. 文件路径必须是**项目内相对路径**（POSIX `/`），不能用 `basename`，也不能用开发机绝对路径；
3. 没有证据时，状态是 `needs_review`，不是「发布」；
4. **同一个不变量只允许有一个实现**——路径规范化只有 `engine/path_utils.py` 一份，
   `engine/business_graph/paths.py` 只是再导出。这条纪律来自一次真实事故（见第十九章 19.2 ①）。

## 三、业务模块必须采用多级结构

以实验室安全项目为例，不能只展示：

```text
用户管理、预约管理、设备管理、安全检查
```

应该继续向下展开：

```text
实验室安全助手
├── 用户与权限管理
│   ├── 用户注册
│   ├── 用户登录
│   ├── 角色管理
│   └── 权限校验
│
├── 实验室使用管理
│   ├── 实验室预约
│   │   ├── 提交预约
│   │   ├── 时间冲突检测
│   │   ├── 预约审批
│   │   ├── 预约取消
│   │   └── 预约状态流转
│   └── 使用记录管理
│
├── 设备管理
│   ├── 设备入库
│   ├── 设备借用
│   ├── 设备归还
│   └── 设备维修
│
└── 安全检查管理
    ├── 检查任务创建
    ├── 隐患登记
    ├── 整改任务分配
    ├── 整改结果提交
    └── 复核关闭
```

### 3.1 一级 / 二级的判定口径（必须先定死，否则「多级」是空话）

| 层级 | 定义 | 判定依据（全部可复现） |
|---|---|---|
| 一级：业务域 | 一个**独立业务目标**，有自己管理的业务对象和状态 | 目录 / 包名；类名与文件名词根；类 / 模块中文 docstring；调用社区；共同写同一状态对象 |
| 二级：功能模块 | 域内一个**可独立命名、可独立验收**的能力，通常对应 1~5 个函数 | 函数名动词词根、状态写入目标、函数间调用簇、docstring 首句 |
| 动作 | 二级功能下的具体函数 | AST 函数定义 + 行号 |

**判定不出二级时必须诚实降级：** 若某域内可识别能力数 < 3，则该域只做一级展示，并标记 `hierarchy: flat`。
**不允许为了「看起来有多级」而硬拆。**（真实项目上确实大量退化：flask 7/12 个域是 flat、urllib3 5/19。）

### 3.2 每个模块都必须有一张「业务模块卡片」

卡片共 13 个字段，其中**「不负责什么」是最重要的一个**：

| 字段 | 示例 | 置信度 |
|---|---|---|
| 中文名称 | 时间冲突检测 | inferred（可被教师改名） |
| 所属模块 | 实验室预约 | verified |
| 模块目标 | 防止同一实验室同一时间被重复预约 | unconfirmed（需教师确认） |
| 输入 | 实验室、开始时间、结束时间 | inferred |
| 输出 | 可预约 / 冲突 | inferred |
| 业务规则 | 时间区间不能与已有预约重叠 | verified（绑定 `if start < res_end and end > res_start`，`reservation_manager.py:122`） |
| 上游模块 | 提交预约 | verified（调用图） |
| 下游模块 | 审批流程 | verified（调用图） |
| 状态变化 | 预约状态保持待审批或被拒绝 | verified（状态追踪） |
| **不负责什么** | 不负责审批权限判断 | inferred → 待教师审核 |
| 实现证据 | 文件、类、函数、代码行 | verified |
| 可信度 | 已确认 / 系统推断 / 待教师审核 | — |

> **「不负责什么」非常重要**：它能训练学生建立模块边界，而不是把所有功能都堆进一个模块。
> 它也是全套 UI 里最有记忆点的一个字段（答辩演示必讲）。
> 生成规则见第八章 8.6。

## 四、学生的学习流程：理解—拆解—设计—答辩（六阶段）

> **贯穿六个阶段的一条交互铁律：学生先输出，系统后反馈。**
> 任何「先给答案再问学生」的设计，都会把训练退化成阅读。

```text
① 项目认知  →  ② 模块卡片学习  →  ③ 业务流程推演
    →  ④ 学生自己设计模块  →  ⑤ 系统评审与教师点评  →  ⑥ 重构挑战
```

### 阶段一：项目认知

系统先给学生展示：项目要解决什么问题 / 服务哪些角色 / 有哪些一级模块 / 模块之间如何协作 /
当前项目有多少层级 / 哪些是核心模块 / 哪些只是支撑模块。

学生完成的不是选择题，而是一次「项目地图阅读」。目标是让学生能够回答：

> 这个项目为什么需要这些模块？

**交互方式：** 学生用自己的话写出答案 → 系统只输出**覆盖度报告**（命中了哪些域的 objective、漏了哪些域），
**不打分、不给「标准答案」**。

> **阶段一已落地（Sprint 3）**，实现位置与口径：
> 判定在 `engine/teaching/coverage.py:295`（`evaluate_orientation`，纯规则、无 LLM、确定性），
> 接口是 `POST /api/projects/{id}/teaching/orientation/coverage`（`backend/app/main.py:255`），
> 前端是 `frontend/src/components/StageOrientation.vue`（反馈区 `v-if="report"`，
> 提交前一个节点都不渲染）。
>
> **本阶段真实的比对口径（必须如实写，别包装）**：
> 比对键只有两个来源——**域名**（`domain_name`，剥掉「模块 / 管理 / 系统 / 的」等结构性词）
> 与**域目标文本**（`domain_objective`）；置信度为 `unconfirmed` 的字段**不参与比对**，
> 该域进 `not_comparable` 并写明原因。
> **当前两个演示项目的域目标全是空的**（引擎推不出业务含义就不编），所以实际比对**只用域名**——
> 也就是说"命中"目前只代表学生提到了这个模块的名字。这是阶段一现阶段最大的短板，
> 教师一旦填上 `objective`，它会自动参与比对（无需改代码）。
>
> **做不到的直接写出来**：系统**不做中文分词**，所以报告里没有「你额外提到了哪些模块」这类结论；
> 命中 ≠ 答对（是否理解该模块为什么存在，规则引擎判不了，交教师）。

### 阶段二：模块递进学习

系统逐层打开模块。例如进入「实验室预约」后，继续学习：

```text
实验室预约
├── 提交预约
├── 查询已有预约
├── 冲突检测
├── 权限确认
├── 审批处理
└── 取消预约
```

每个小模块都经过五个问题：

1. 它要解决什么问题？
2. 它接收什么输入？
3. 它输出什么结果？
4. 它改变了什么状态？
5. **它为什么不应该和其他模块合并？**

学生必须用自己的话回答，系统再根据模块卡和代码证据进行评价。

**评价口径（重要，防止 AI 讨好）：** 系统只做**事实覆盖比对**——学生提到的关键事实
（状态字段名、规则条件、上下游模块名）是否出现在卡片的 `verified` 字段里。
**卡片本身置信度不足的字段不参与判分，改提示「该卡片待教师确认」。**

> **阶段二已落地（Sprint 4）**，实现位置与口径：
> 判定在 `engine/teaching/card_coverage.py`（`build_module_card_task` / `evaluate_module_card_answers`，
> `algorithm_version = card-coverage-1.0`、`scoring = fact_coverage_only`、`has_score: false`）；
> 题目文本与「问题 → 参与比对的卡片字段」映射**外置在 `engine/lexicon/stage_questions.json`**
> （教师改问法或换比对字段不用改引擎，也不用改前端）；
> 接口是 `GET/POST /api/projects/{id}/teaching/module-card/{task,coverage}`
> （`backend/app/main.py:281` / `:298`）；前端是 `frontend/src/components/StageModuleCard.vue`
> （阶段二视图，挂在培训工作区 `TrainingView.vue` 里；在「阶段主线」这一组里是**第二个页签**，
> 页签分组与默认落地页见 `docs/04-api-and-frontend.md` §12.1）。
>
> **与本段上面那句原话的一处偏差，必须写明**：培养方案写的是"比对卡片的 `verified` 字段"，
> 实现口径是**只有 `unconfirmed` 被挡在门外**，`inferred` / `from_docstring` 这类字段**参与**比对，
> 但每个比对键都带 `origin_confidence`，UI 必须把徽章显示出来。
> 理由：阶段一已经是这条口径（`engine/teaching/coverage.py` 的 `_UNCONFIRMED_TOKENS`），
> **同一个仓库里不允许有两套"什么算没确认"的判定**。要更严，把字段置信度改成 `unconfirmed`
> 或改词典映射即可，不需要改代码。
>
> **三条做不到的（写在报告的 caveats 里）**：①「提到」不等于「理解」，抄卡片也能命中；
> ② 不做中文分词，给不出"你额外提到了什么"；③ 规则条件类的比对键是**代码表达式**
> （引擎只给代码、不编语义），中文表述通常命中不了，因此**该类键未命中不构成答错的证据**。
>
> **一处刻意的界面取舍（会被问，先写清楚）**：业务图谱页里卡片是全字段可见的，
> 但在阶段二，**卡片内容默认收起**，学生点「展开卡片内容」才显示（提交后不再隐藏）。
> 理由：把卡片摊开放在问题旁边，学生会直接抄，训练就退化成阅读——而 §12.6 第 1 条要求
> 「反馈区域在提交前不渲染」。这里把"看卡片"变成学生**主动**的动作：
> 想对照随时能看，默认状态尊重"先自己想"。走查对这个行为有断言
> （提交前 `[data-test="module-card-reveal-panel"]` 不存在、点开后出现）。

### 阶段三：业务流程推演

系统给学生一个真实场景：

> 学生申请预约实验室，但该时间段已经有其他预约。

学生需要自己推演：

```text
提交预约 → 查询已有预约 → 检查时间冲突 → 返回冲突提示 → 预约创建失败
```

换一个场景：

> 学生申请预约，时间没有冲突，但该学生不是实验室负责人。

流程变成：

```text
提交预约 → 查询已有预约 → 冲突检测通过 → 权限校验失败 → 拒绝提交
```

训练重点是：业务模块顺序 / 模块之间的数据传递 / 条件变化后的路径变化 /
哪个模块应该承担哪一种判断 / 哪个模块不应该越权处理其他职责。

**产出的流程必须优先取「真实业务路径」，不能取 initialization / seed 流程**——
教学生「核心业务 = 造样例数据」是教学性错误。生命周期降权规则见第八章 8.7。

### 阶段四：学生自己设计模块（**系统最重要的创新部分**）

系统给学生一个**新需求**，而不是直接给出原项目结构：

> 请为「高校实验室设备借用系统」设计核心业务模块。

学生需要自己完成：

```text
设备借用系统
├── 用户权限
├── 设备目录
├── 借用申请
├── 库存状态
├── 审批流程
├── 归还确认
└── 异常处理
```

然后为每个模块填写：中文名称、模块目标、输入输出、依赖模块、状态变化、业务规则、异常情况、
**不负责的内容**。

系统不能只判断「和标准答案是否完全一致」，因为业务设计存在多种合理方案。
应采用「标准逻辑图 + 可接受替代结构」：

```text
必须存在：
- 用户身份或权限
- 设备状态
- 借用申请
- 归还处理

可选结构：
- 审批可以独立成模块，也可以归入借用流程
- 异常处理可以独立，也可以作为状态管理的一部分
```

**这比固定选择题更能培养设计思维。**

> **实现状态（Sprint 5）**：本节描述的「新需求 + 自己拆模块 + 必填字段」已落地
> —— 题干预设在 `engine/lexicon/design_tasks.json`（按复杂度级别给不同任务类型），
> 画布在 `frontend/src/components/StageDesign.vue`，判定在 `engine/design/task_builder.py` +
> `matcher.py`。**「可接受替代结构」这一条只在教师种子给出时生效**（`alternatives.py`），
> 种子为空时引擎明确报 `available = False`，**不假装判过**。
>
> **优先级 3.5 一轮的进展**：`lab_safety_assistant` 已经有了一份教师确认过的任务种子
> （10 项必备能力 + 2 条必备依赖 + 2 个必备边界 + 2 条可接受替代结构 + 1 条禁止合并项），
> 所以这一节描述的「标准逻辑图 + 可接受替代结构」在该项目上**真的在判**了；
> `python_dotenv` 仍然是自动提炼 + 「待教师确认」。**两个项目的口径不同，演示时要说清是哪一个**。

### 阶段五：系统对学生设计进行评审

学生提交设计后，系统从六个方面评价：

| 评价维度 | 权重 |
|---|---:|
| 核心需求覆盖度 | 25% |
| 模块职责清晰度 | 20% |
| 层级结构合理性 | 15% |
| 模块依赖和流程完整性 | 20% |
| 异常和边界情况 | 10% |
| 设计理由与证据 | 10% |

（可计算定义见第九章 9.2；权重与 `DesignTask.rubric_weights` 一致。）

系统输出的反馈不能只是「得分 78」，而应该是：

> 你已经覆盖了设备借用的主流程，但没有处理「归还后设备状态恢复」的问题，
> 因此设备状态模块和归还模块之间缺少状态回写关系。

或者：

> 「审批处理」同时负责权限判断、时间冲突检查和状态更新，职责过重，
> 建议拆分为权限校验、冲突检测和审批状态三个模块。

**这才是真正的业务逻辑训练。**

> ⚠️ **每一条反馈都必须能追溯到一个可计算信号。**
> 不允许出现「模型觉得这个设计不够优雅」这类无依据反馈。
> 反馈必须是「信号码 → 中文模板」的纯函数映射，每条都写明它由哪个信号触发（见第九章 9.2）。

> **实现状态（Sprint 5）**：六维**全部**落地（不是只做可计算的三维），
> 实现见 `engine/design/rubric.py`；`status = not_evaluated` 的维度返回 `score: null` 并附原因，
> **不参与权重归一化**（`weights_renormalized = true`），页面上如实显示「本轮未评估」。
> 每一维的 `findings` / `issues` / `signals` 都能对上：`issues` 恒等于
> `feedback.render_issues(signals)`（`scripts/test_design_rubric.py` 逐维断言这条恒等式）。
> 唯一的例外是第 5 维「未填按 0 计并标注 `not_filled`」——那是 README §9.2 明写的口径，
> 因为「还没有填」与「算不出来」不是一回事。

### 阶段六：重构挑战

系统追加需求：

> 现在增加「教师审批」。
> 或者：现在要求「设备损坏时禁止归还完成」。

学生需要修改原有模块结构和流程。**如果学生只能理解原项目，却不能应对新需求，
说明他还没有形成真正的业务逻辑能力。**

> **「四关训练」在新方案中的位置**：四关（功能拆分 / 职责理解 / 流程推演 / 实现思路）
> 不再是独立的关卡页面，而是降级为四类**学习目标**，由上面六个阶段的数据驱动实现。
> 四关时代记录的「典型错误」仍然有效，可以直接当教学设计素材：
> 漏模块 / 模块粒度不合理 / 边界模糊；职责理解偏差 / 不知道输入输出；
> 路径错误 / 漏掉关键步骤；知道做什么但不知道怎么做。

## 五、项目大小必须决定训练门槛（复杂度分级 L1–L4）

项目不能统一用四关题处理。用项目复杂度自动分级，教师可以手动覆盖。
**定级按结构定义来算，不按分支数量算**（这是被真实数据纠正过的口径，见第十九章 19.2 ④）。

| Level | 定义 | 训练内容 |
|---|---|---|
| **L1 基础项目** | 1—5 个一级模块；只有一条主流程；状态变化较少；没有复杂权限和外部系统 | 识别一级模块；给模块写中文释义；画简单模块树；设计一条主流程 |
| **L2 多模块项目** | 5—10 个一级模块；存在多个二级模块；有用户、数据和基础状态；存在跨模块调用 | 一级/二级拆解；模块职责边界；输入输出设计；模块依赖；业务流程排序 |
| **L3 复杂业务项目** | 10—25 个模块；多角色；多条业务流程；状态流转明显；存在权限、审批、异常和回滚 | 多场景推演；状态机设计；正常流程与异常流程；模块边界重构；比较两种架构方案 |
| **L4 综合设计项目** | 25 个以上模块；多个外部系统；动态调用或复杂数据流；多角色协作；跨领域业务 | 从需求独立设计完整业务架构；设计多个候选方案；分析耦合、扩展性和风险；答辩；根据新需求重构原有设计 |

### 5.1 复杂度必须可计算，且必须显示明细

```text
complexity_raw =
    1.0 × 一级业务域数
  + 1.5 × 二级功能点数
  + 0.8 × 跨域调用边数
  + 0.6 × 被写入的状态字段数
  + 0.4 × 业务分支数（if / raise）
  + 1.0 × 外部入口数
  + 1.2 × 角色数（角色 / 权限词表命中）
```

`complexity_raw` 是**跨项目比较的辅助分**，不是定级依据。定级依据是结构定义
（一级模块数 + 二级模块数 + 角色数 + 审批类能力 + 状态字段数），并写进 `level_basis` 供教师复核。

初始阈值（**必须标注为待实测校准**）：

| 级别 | `complexity_raw` | 典型形态 |
|---|---|---|
| L1 | < 12 | 单文件脚本、单类小工具 |
| L2 | 12 – 40 | 多模块教学项目 |
| L3 | 40 – 90 | 多角色业务系统 |
| L4 | ≥ 90 | 多系统协作的大型项目 |

**UI 要求：** 显示级别徽章 + 点开显示七个维度的分项数值 + 公式 + 算法版本号 + caveat
（前端实现：`ComplexityBadge.vue`）。

> **阈值纪律**：当前阈值只经过 4 个项目，**必须标注为「待实测校准」**，
> **不许把它包装成「AI 智能评估项目难度」**。
>
> **小项目不能生成过重的训练，复杂项目也不能只给四道题。**

## 六、教师应该成为「课程设计者」，不是只看最终分数

```text
上传项目
→ 系统自动分析
→ 教师确认核心模块
→ 教师修正中文释义
→ 标记必学模块和选学模块
→ 设置训练门槛
→ 发布给学生
→ 查看学生设计和薄弱点
```

教师可以对每个模块标记：核心 / 支撑 / 可选 / 暂不讲解 / 必须掌握 / 容易误解 / 需要人工说明。

教师还可以设置「标准逻辑图」（Gold Graph）：

```text
必选节点 / 可选节点 / 可接受替代结构 / 禁止合并节点 / 必须存在的依赖关系 / 必须处理的边界场景
```

**这样系统不会把一种架构方案当成唯一真理，同时又能保证评价有依据。**

### 6.1 审核状态与版本纪律

- 状态：`draft` / `needs_review` / `approved` / `rejected`；
- 教师确认后的版本要**绑定分析版本和源码哈希**
  （`analysis_version` + `source_hash` + `reviewed_by` + `reviewed_at` + `fields_locked`）；
- 重新分析后如果哈希变化，**旧审核不能静默覆盖新结果**，必须返回 `review_status = "stale"`，
  提示「源码已变化，以下 N 项审核需要复核」。

> 现状：只有「关键实现逐条确认 / 拒绝」已实现并持久化（`localStorage['teacher_review_status']`）；
> **模块改名、图谱审核、Gold Graph 编辑器都还没做**——不要写成已完成。

### 6.2 学生界面绝不能出现的东西

- 内部评分公式的全部权重；
- 未审核的推断结论（必须带「待教师确认」标记）；
- 其他学生的答案与设计方案；
- 直接可读取的标准答案字段（`correct_answers` / `explanation`）；
- 只为算法调试服务的内部异常堆栈与 `_inferred_` 之类实现标记。

### 6.3 发布前的自动检查（TeachingValidator，九条）

任何教学材料进入学生视图前，都必须过这九条：

1. 每个解释至少有一个证据；
2. 每个证据文件存在，且行号在文件范围内；
3. 每个 `return` 节点的后继为空或标记为不可达；
4. 题目引用的节点存在；
5. 标准答案属于该节点的合法下一步；
6. 提示没有直接引用不存在的变量；
7. 实际源码与 `source_hash` 一致；
8. **不能把 `inferred` 事实显示成 `verified`**；
9. 没有可用证据时，课程状态是 `needs_review` 而不是 `published`。
