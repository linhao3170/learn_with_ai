### 19.2 开发过程中被真实数据纠正的设计错误（累计 21 条）
**这些全都是「跑起来才发现」的，看代码看不出来。**
它们也是「为什么要写测试而不是靠肉眼看输出」的最好论据。

| # | 问题 | 修正 |
|---|---|---|
| ① | **读错了字段名**：`PythonParser` 把文件级 docstring 放在 `parsed.module_docstring`，代码读的是 `parsed.docstring` → 所有中文域名丢失，退化成英文词根 | 修正后域名才变成作者写的中文 |
| ② | **域聚类只做了「投票」，忘了「合并」**：`MERGE_THRESHOLD` 声明了却从未使用 → python-dotenv 里**每个类都成了一个业务域**（16 个） | 补上并查集合并，降到 6 个 |
| ③ | **合并信号过强**：`_next_id` 这种记账属性被当成「共享业务状态」，`manager` 这种架构后缀被当成共同词元 → 用户 / 预约 / 设备三个域被粘成一个 | 过滤 `_` 前缀记账状态、过滤架构后缀词元、`shared_token` 权重降到 1 |

**Sprint 5 又补上四条（同一类：都是"跑起来才发现"，其中两条是走查断言抓出来的）**

| # | 问题 | 修正 |
|---|---|---|
| ⑬ | **一个模块靠"名字像"同时算作多项必备能力的承担者**：必备能力叫「普通能力一 / 二 / 三」时，学生画的「普通能力一」与另两项的中文 bigram 交并比是 3/5 = 0.6 ≥ 0.5，于是**一个模块凭空覆盖了三项能力**，覆盖率被抬高（合成用例第一次跑就复现：期望 matched=1，实得 3） | `matcher.match_modules` 改成两遍：**先算出一个模块对全部必备能力的「最强命中方式」，再只保留该方式的配对**。同一种方式下**仍允许多项**（一个模块确实能承担多项能力，「职责过载」正是靠这一点才能被检出），更弱的方式不再叠加 |
| ⑭ | **空画布被算成 0 分**：一个模块都没有时，覆盖度 0/8 记 0 分、「异常与边界」因为「未填」也记 0 分，于是总分 0.0 —— 而「没交设计」被读成「设计得零分」是完全不同的两件事（违反的正是本项目自己的第 5 条设计原则：算不出来不许填 0） | 空提交时**六维全部 `not_evaluated`、`overall_score = null`**，并给出「请先在画布上添加模块」；后端同时在入口 400 拒绝空提交（两道闸，互不代替） |
| ⑮ | **「只画线、不填 `depends_on`」被当成「声明与画线不一致」**：画布上画的线本身就是依赖声明，所以这条规则会把**每一个正常使用画布的学生**都扣分（典型的假阳性 —— 和 §19.2 前三轮那些"看起来合理的规则"是同一类错误） | `graph_checks.declared_vs_drawn` **只在两边都非空且内容不同时**才报；「只画线」与「只写字段」都不算不一致，并把这条理由写进函数 docstring |
| ⑯ | **第二次提交的 iteration 退回 1**：`submit()` 里先 `report.value = null`（为了不把旧结论留在屏幕上）**再**构造提交，而 iteration 是从 `report` 算的 → 第二次提交仍显示「第 1 次提交」。**是走查里那条「iteration 递增且出现对比条」的断言抓出来的**：页面上对比条自己出现了、标题却写着第 1 次，自相矛盾 | 改为 `iteration = history.length + 1`，并把「先构造提交、再清空报告」的顺序写进注释（顺序本身就是这个 bug 的成因） |

> 四条里 **⑬⑭ 直接损害评审的正确性**（覆盖率虚高、0 分被误读），
> **⑮⑯ 直接损害可用性**（正常操作被扣分、第二次提交看起来像第一次）。
> ⑬ 是合成用例抓的、⑭ 是"空提交"这个边界抓的、⑮ 是把规则想清楚之后自己发现的、
> ⑯ 是走查断言抓的 —— 又一次说明本项目那条老结论：**光看代码看不出这些，必须让真实输入跑一遍。**

### 19.3 反直觉但必要的实现（不要当成 bug 删掉）

1. **记账状态**（`_` 前缀，如 `_next_id`）**不算**「共享业务状态」；
2. **架构后缀**（`manager` / `service` / `checker`…）**不算**共同词元；
3. **目录只有在文件数 ≤ 5 时**才允许「整个目录 = 一个业务域」；
4. **编排类判定要排除构造函数**：`LabSafetyApp.__init__` 里写的是「装配」
   （`self.user_manager = UserManager()`），不是业务状态，不排除它编排类识别会全部失效；
5. **`to_rel` 必须幂等**：绝对路径才转、相对路径原样返回；唯一实现在 `engine/path_utils.py`，
   **不要在别处再写一份**；
6. **「状态字段名」是从事实文本里解析出来的**（Sprint 4 新增）：状态变化事实长这样——
   `f"{symbol} 写入 {attr}"`（`engine/business_graph/facts.py:120`），阶段二要拿它当比对键，
   就得取**最后一个 `" 写入 "` 之后那一段**并过一遍路径正则（`card_coverage.extract_state_path`）。
   解析不出来时**退回整条文本当键**，并把这个退化情况如实打出来（走查实测：63/63、8/8 全部可解析）。
   **不许为了好看而假装解析成功**——那会让学生答对了却判未命中；
7. **未知问题标识在后端直接 400**（Sprint 4 新增）：引擎其实会把它们列进
   `unknown_question_ids`，但路由层选择**拒绝**。理由：学生写下的内容**绝不能因为前端 key 写错
   就被静默排除在比对之外**——"少比了一问"和"答错了"在覆盖清单里看起来是一样的。
   （所以 `unknown_question_ids` 走接口时通常恒为空；它保留在引擎层，供纯函数调用者使用。）
8. **`DesignPatternClass.instance_attributes` 是 `Set[str]`，读取时必须走
   `sorted_instance_attributes`**（优先级 4 二轮新增）：**不要**把它换成"直接在 6 处加 `sorted()`"
   的写法，也不要因为看到"排序看着多余"就删掉 —— 它是 §19.2 ⑳ 那个跨进程不确定性缺陷的修复点。
   只判"在不在集合里"（`in`）的地方不受影响，可以继续用原字段；
   凡是"遍历它 → 拼进文本"的地方都必须用排序版。

### 19.4 走查与前端工程的两个易错点

- `[data-test="graph-domain-toggle"]` 上有 `@click.stop`（展开），**行本身**才是「选中」。
  点错元素会表现为「模块卡片打不开」；
- Vue 会把 `<template>` 里的 HTML 注释编译成 comment vnode **真的渲染进 DOM**。
  注释里写 `correct_answers` 字样会让「DOM 不含答案」的断言**假失败**
  （说明文字应放进 `<script setup>`）。

**UI 重设计一轮又补了同一类的两个变体（都是"看不见却真的在 DOM 里"）**

3. **折叠起来的抽屉，内容仍然在 DOM 里**：这一轮把口径说明收进了可折叠抽屉
   （`.drawer-body` 用 `grid-template-rows: 0fr` 收起），视觉上"收起来了"，
   但 `textContent` 与 `outerHTML` 里**一个字都不少**。所以
   **"收起"不能当成"没写"**：边界纪律（不许出现答案字段名、内部 key、必备能力全文）
   对**所有**文案生效，包括用户要主动点开才看得到的那些。走查的断言也正是在这个前提下写的 ——
   `来源依据默认收起（且内容仍完整在 DOM 里）` 一条同时钉住了"默认不占第一屏"与"证据没被删"。
4. **同一句禁令写进文案就会踩断言**（§19.1 第 23 条是实际发生的那次）。写"不许出现 X"
   这类说明时，**不要把 X 本身逐字写进渲染的文案**（`<template>` 注释里也不行）；
   要提就写中文描述（"答案字段名"/"内部 key"），把字面量留在 `<script setup>` 的注释里。
   这不是文字游戏：那条断言检查的是"页面上有没有出现这个字段名"，它无法区分泄漏与提及 ——
   而**放宽断言比改一句文案危险得多**（前者会让真正的泄漏再也报不出来）。
