## 十三、纪律与边界

### 13.1 表述纪律：不许说 vs 应该说

做汇报、答辩、写申报书时，**严格按下面的表格表述，不许越界**：

| ❌ 不许说 | ✅ 应该说 |
|---|---|
| 「分析准确率 95%」 | 「事实层来自 AST 直接解析，可复现；语义层标注为待确认」 |
| 「我们比 ChatGPT 更准」 | 「与 ChatGPT 相比，我们的答案可复现、可定位、可被改写」 |
| 「节省教师 80% 备课时间」 | 「把备课中的机械整理工作自动化，效果需实测」（没有实测数据就不说数字） |
| 「支持各类项目」 | 「当前仅支持 Python；已实测 N 个真实项目」 |
| 「AI 自动评分」 | 「可判定题由规则引擎判分；开放题只出覆盖度报告，不评分」 |
| 「设计题 AI 智能评分」 | 「设计题用六维评估框架给维度反馈与改进建议，设计没有唯一正确答案」 |
| 「六维评分证明了他的业务能力」 | 「六维是**结构信号**：本轮评估覆盖了 N/6 维，未评估的维度页面上原样列出；学生对业务的理解由教师与答辩判断」 |
| 「他设计得了 82 分」 | 「本轮 5/6 维可计算、权重已按比例归一化，总分 82；其中『层级结构合理性』因未建立层级关系本轮未评估——**分数只覆盖算得出来的那部分**」（Sprint 5 起设计层真的有分数了，这一条是新增的表述纪律） |
| 「系统发现他漏了归还处理」 | 「系统**未在他的设计里识别到**『归还处理』（可能是命名不同，词汇匹配必然有假阴性）」 |
| 「系统能自动发现真实核心业务」 | 「系统输出可复现的业务优先级排序，作为教师讲解顺序的参考信号」 |
| 「我们用了 AI 做分析」 | 「规则引擎做事实，LLM 只做语义润色和事实映射」 |

**纪律的意义：** 评委和教师见过太多「AI 驱动、智能分析、精准高效」的项目。
**说清楚自己哪里不行，反而是最稀缺的竞争力。**

### 13.2 证据纪律

1. **不美化数据。** 这是最危险的一条。错误率高不丢人，「我们实测发现某一层错误率很高，
   所以我们把它降级为待确认」是加分项；编一个好看的假数字，被追问一句就垮。
2. **不许在自造样本上报告准确率。** 样本里的启发式规则（`if "conflict" in name`）就是照着这个样本调的，
   **在这个样本上报告准确率 = 在训练集上报告测试准确率**。
3. **数字必须能回指。** 材料里出现的每一个数字都要能指回 `validation/` 下的原始记录文件。
4. **事实与推断分层，不混着说一个总准确率。** 三层判定主体不同（见 13.4），就必须分开说。

### 13.3 AI 的边界（豆腐问题）

**AI 评测会不会一直迎合学生？** 这是设计上必须专门规避的：

> 我们的做法是：**不让 AI 判断「对不对」，只让它抽取「学生提到了哪些事实」**，然后跟事实表做比对。
> AI 的工作从「判断对错」降级成了「事实映射」，它没有空间去迎合。
> 而且提示词里写死：判断不了必须输出 `unknown`，**不允许为了让学生感觉良好而给出正向判定**。
> 设计题更是这样，AI 只做维度评估，不做「好不好」的绝对判断。
> **覆盖度是可核验的，分数不是。**

> **实现比这句话还保守（Sprint 3 / 4 已落地，据实说明）**：阶段一 / 二的覆盖比对**根本没有用 LLM**——
> 它是纯规则的键命中（`engine/teaching/coverage.py` 的 `key_hit`：中文按子串、英文按整词）。
> 连"抽取学生提到了哪些事实"这一步都没交给模型，而是问"学生写的话里是否出现了**图谱里已经存在的**
> 比对键"。所以对外表述应当再降一档：**不是"AI 只做事实映射"，而是"这两步都没有 AI"**。
> 相应地，能力上限也如实说：**命中 ≠ 理解**（抄卡片也能命中），系统不做语义判定。

**绝不能交给 LLM 的事：**

- 事实表的正确性判定；
- 设计题的最终评分逻辑（Rubric 框架必须是人定的）；
- 任何涉及「判定对错」的事情；
- 核心算法的实现（可以让它写草图，但必须自己验证）。

**可以交给 LLM 的事：** 中文名称润色、题干初稿、模块卡片参考文本（必须经教师审核）、
讲解稿、PPT 文案、前端样式、测试用例草稿、错误信息友好化。

**信任基础的三根支柱：** 答案可复现 / 答案可追溯 / **教师有一票否决权**。
第三点目前只实现了一半（关键实现可确认 / 拒绝并持久化，模块与图谱的审核还没做），
但它恰恰是最能打动教师的功能。

### 13.4 三层判定主体分离

评测拆成三层，**判定主体不一样，报告时也要分开报**：

| 层 | 占题库比例 | 谁来判 | 是否调 LLM |
|---|---|---|---|
| 第一层：可判定题（调用顺序、模块归属、状态字段变更） | 60–70% | 规则引擎 | ❌ 不调，确定性 100% |
| 第二层：语义理解题（职责命名、流程命名） | 其余 | **答案必须经教师确认才入答案库** | 可辅助出题，不可判分 |
| 第三层：设计题 | — | 六维维度评估，**不打对错分** | 仅做事实映射与文本整理 |

> 第一层回答「数据哪来」：**数据来自代码本身，不来自 AI**。判分是集合比对，不是语义判断。
> 第二层的纪律是：**题可以 AI 出，答案必须有人背书。**

### 13.5 不许硬做半成品上台

> **能做完的写进计划，做不完的诚实标「进行中」，不许硬做半成品上台。**

推论：

- 设计画布的六维反馈如果只有模板、没有真实信号 → 说「反馈模板已实现，匹配逻辑基于学生提交的模块结构，
  完整 Rubric 引擎在 Sprint N」；
- 自动业务图谱如果还没跑通 → 就用手工 / 教师种子图谱演示，**但要在 UI 上标明这是「教师审核版」**，
  不能说成「系统自动生成」。

**明确不许上台的半成品：** 六维里填假分的维度、自动生成图谱但未标注「待审核」、
反馈模板但说不清触发信号、画布只能拖不能提交。

### 13.6 红线（违反一次，整个项目的可信度就没了）

1. **不许让 LLM 判定对错、给分数、或生成评分基准。**
2. **不许给算不出来的维度填分数**（必须 `not_evaluated`）。
3. **不许在自造样本上报告准确率。**
4. **不许把未审核的推断展示为已确认事实**（`needs_review` / `source: auto` 必须一直可见）。
5. **不许把 `correct_answers` 下发到浏览器。**
6. **不许在任何契约里出现开发机绝对路径。**
7. **不许把「计划中」的能力写成「已完成」。**
8. **不许美化数据。**

**另加两条从真实开发中踩出来的经验：**

9. **同一个不变量只允许有一个实现。** 路径规范化曾经有两份，只修了一份，
   导致图谱里 **1054 处**路径变成 `../../xxx.py`（见第十九章 19.2 ①）。
10. **「跑起来」才算验证过。** 业务图谱这一轮有 **8 处**设计错误是靠跑真实项目发现的，
    看代码看不出来（见第十九章 19.2）。改完引擎，**必须**在 4 个项目上重跑
    `python scripts/validate_business_graph.py`。

### 13.7 不承诺清单

- 不承诺自动理解所有项目的真实业务含义；
- 不承诺自动生成完全正确的自然语言场景；
- 不承诺用一个总分证明学生真正掌握了项目；
- 不承诺支持所有编程语言和动态调用；
- 不承诺不经教师审核就能生成可直接用于课程的教学材料；
- **不承诺「覆盖清单命中」等于「学生答对了」**：阶段一只说明学生提到了哪些模块，
  是否理解该模块为什么存在，规则引擎判不了（`engine/teaching/coverage.py` 里没有语义判定）；
- **不承诺能列出「学生额外提到的模块」**：系统不做中文分词，
  所以报告只给"命中 / 未命中 / 未参与比对"三份清单，不猜学生话里的新名词。

**最重要的一条**：这个系统的核心竞争力不是「讲得像老师」，而是
**把老师带学生学项目时的完整思维过程结构化**——先建立业务模型，再看代码证据；
先理解现有结构，再自己动手设计；先做静态拆分，再做动态流程；先独立完成，再面对变更重构。

## 十五、答辩与演示

### 15.1 四个必答题

**Q1：这个能力，为什么不做成一个提示词 / 一个 Skill 就行？**

> 我们验证过，其中一部分能力确实应该做成 Skill，我们也已经做了。但有四件事提示词做不到：
> 第一，**可复现**——同样的代码问十次，提示词给十个不一样的答案，我们是同一个答案；
> 第二，**可定位**——每条结论能回指到第几行，教师可以审核；
> 第三，**可沉淀**——教师改过的结论能固化，下次重新生成不一；
> 第四，**设计能力培养**——提示词能给你一份分析，但不能带着学生一步步从「看懂」走到「自己会设计」。
> 还有一条物理限制：**一个 20 万行的项目塞不进上下文窗口**，塞不进去模型就会编。
> 我们的引擎做一次结构化索引复用一万次，索引里没有的东西我们不说。

**Q2：评测的数据从哪来？凭什么当评分标准？**

> 见 13.4 的三层拆分。补充一句：设计题我们不叫「准确率」，叫「维度评估」，
> 并明确告诉学生设计没有唯一正确答案。

**Q3：AI 评测会不会一直迎合学生？**

> 见 13.3。

**Q4：这不就是另一个代码分析工具吗？有什么独特的？**

> 代码分析工具我们也用过，它们给你的是调用图、类图、复杂度——这些都是「代码长什么样」。
> **我们给学生的是「业务为什么长这样」。**
> 我们有两张图谱：一张是代码实现图谱（文件、函数、调用），另一张是**业务逻辑图谱**（模块、职责、规则、边界）。
> 学生先学业务层，理解每个模块为什么存在、负责什么、不负责什么，再用代码层做证据验证。
> 最终目标不是「看懂这个项目」，而是**学生能为一个全新的需求自己设计出合理的模块结构**。

### 15.2 常见追问

| 追问 | 答法要点 |
|---|---|
| 准确率多少？ | 分三层答：事实层 AST 直解可复现；语义层标「待教师确认」；设计层不谈准确率，谈六维维度反馈。**并且主动说明人工核对还没做完，所以现在不报准确率** |
| 只支持 Python？我们学校教 Java | 诚实说只支持 Python；**但核心培养模式——业务图谱、模块设计、重构挑战——是跨语言的，换语言只需换 parser，教学法层不改** |
| 设计题怎么评分？设计没有标准答案 | 六维评估 + 可接受替代结构；两种都算对，系统只提醒权衡，不判错 |
| 和软件工程课有什么区别？不就是教模块化吗 | 软件工程课教概念，学生听了都懂，一到真实项目还是不会拆。我们把概念落地成训练动作 + **有人给你纠正动作**（就像学游泳） |
| 教师会愿意用吗？愿意付钱吗 | 单教师付费意愿低，我们很清楚。真实采购单位是**系 / 教研室 / 课程组**，动机是教改申报、一流课程、工程教育认证的**课程目标达成度证据** |
| 这个技术门槛在哪？ | 单点都不难，积累在于**把证据串成一条可复现链路**：代码 → 事实表 → 业务图谱 → 设计训练 → 六维反馈；**更重要的门槛不在技术，在培养模式本身** |
| 能落地吗？有没有实际用过？ | 诚实说**目前还没有真实教师用户**；已完成的是在 3 个真实第三方项目上的分析验证；下一步是找 2–3 位真实教师试用 |
| 这和我们见过的 XX 工具比怎么样？ | 不争论，直接说差异点：他们停在「图」，我们的落点是**教学材料 + 设计能力培养** |

> 🚩 **「还没有真实用户」这句话必须主动说，不要等评委问出来。** 主动说显得清醒，被问出来显得心虚。

### 15.3 演示动线（业务图谱与设计画布居中，不是彩蛋）

```text
0. 打开【系统主页面】（UI 重设计一轮起是默认落地页）
   "这是我们系统的入口，一共两块核心功能，各占半屏：
    左边【培训系统】是六阶段教学，右边【业务逻辑分析平台】回答'我凭什么这么说'。
    两块共用同一份业务图谱与同一份源码副本（中间这条链就是它俩的关系）。"
   （顺手点开底部【来源依据与口径】再收起）
   "证据与口径默认收在这里 —— 数据从哪来、结论怎么算、哪些还没做，需要时点开就有。
    证据一条都没删，只是不跟主功能抢第一屏。"
   → 这一步一次说清两件事：**功能优先级**（两大块并列、次级入口收成小模块）
     与**诚实边界随手可查**（收起来的抽屉里写的正是"还没做的"）
   → ⚠️ 主页面上的阶段三（流程推演）与阶段六（重构挑战）是**灰的**（未开始，不给入口）：
     别去点它们；被问到就直说"这两阶段还没实现，所以界面上没有入口"——
     这正好是"不许把没做的说成做了"的现场演示
   → 讲完点【进入培训系统 →】进工作区（工作区里五个阶段分成「阶段主线」与「项目视图」两组）

1. 打开项目总览（工作区顶部的项目名与契约行）
   "这是一个真实项目，N 行，M 个一级业务模块。"
   → 先给业务视角，不要一上来给代码

2. 打开【业务模块树 / 业务图谱页签】
   "这是业务图谱——一级业务域、二级功能模块，每个模块都能展开到具体动作。"
   点开一个二级模块，展示模块卡片
   "注意这个字段叫『不负责什么』——我们专门训练学生的模块边界思维。"

3. 点模块卡片里的【实现证据】
   （源码弹窗跳到对应行）"每一条业务结论都能回指到具体代码行。"
   → 这一步证明业务图谱不是编的

4. 打开【项目认知页签】（阶段一，已实现 —— 演示"学生先输出"最便宜的一步）
   先让学生（或现场评委）用自己的话写一句"这个项目为什么需要这些模块"，
   再点提交。
   "注意：提交之前这里没有任何反馈区。提交之后也只给一份覆盖清单——
    你提到了哪几块、还没提到哪几块，**不打分、不给标准答案**。"
   "模块目标那一行如果还是空的，它会老实告诉你『该模块管什么还没有教师确认』——
    引擎推不出业务含义就不编。"
   → 这一步证明的不只是功能，而是"先输出后反馈"和"不编"这两条纪律
   → 现场网络不通时改成：说清"覆盖度比对在后端执行，离线时如实报不可用，不会编一份出来"

5. 打开【模块卡片页签】（阶段二，已实现 —— 卡片五问）
   选一张卡片，按五个问题各写一句（或让评委挑一个问题现场答），提交。
   "它不会说对错，只会告诉你：你写的话里提到了卡片上哪些事实、漏了哪些。
    卡片上还没教师确认的字段**根本不参与比对**，页面会直接标『该卡片待教师确认』。"
   "题目和『哪个问题比哪些字段』都在词典里，换一种问法不用改代码。"
   → 这一步证明"事实覆盖"与"无证据不比对"，是阶段一的加强版
   → **对着追问时的标准回答**：比对键**不全是** `verified` —— 口径是"只有 `unconfirmed` 被挡在门外"，
     每个键都带 `origin_confidence` 徽章，理由见 §4 阶段二末尾（不允许两套"未确认"判定）
   → 现场网络不通时改成：说清"题目与比对都在后端，离线时如实报不可用"（阶段二整页不可用，
     因为题目不在静态快照里，见 0.3 的表格）

6. 打开【流程推演 / 三型场景】
   选一个真实业务场景（不是初始化流程）
   "学生要先自己排出模块顺序，系统只指出第一个分歧点和它的代码证据。"

7. === 【核心杀招】打开【设计画布】（设计层做完之后） ===
   "接下来是最不一样的地方：学生不是被动地看，而是主动地设计。"
   "假设给学生一个新需求——高校实验室设备借用系统，他们需要自己在画布上拆分模块、定义职责、画出流程。"
   （现场快速拖拽几个模块、连几根线、填一张卡，然后点"提交"）
   "提交之后，系统从六个维度给出反馈——不是打个分，而是告诉学生具体哪里有问题：
    『审批处理同时负责权限判断和冲突检测，职责过重，建议拆分。』"

8. 打开【复杂度徽章】
   "系统给项目自动定级 L1–L4，点开能看到七个维度的明细和公式——不是一个黑箱分数。"

9. 打开【能力报告】（做完之后）
   "学生的每一次推演、每一次迭代、六维分的变化都在这里。"

10. 切到【实测证据】
   "目前我们已经在 3 个未参与规则调试的真实第三方项目上跑通了业务图谱生成，
    累计约 2.4 万行代码、67 个源文件；事实层证据完整度 100%，同一份代码两次运行逐字节一致。
    错误类型和占比在 validation/ 下的原始文件里。"
   → 报数字前先核对 validation/ 下的原始文件（见 13.2 第 3 条）

11. 收尾
   "我们的核心优势是：所有事实可复现、可定位、可被教师修改；
    AI 只做外围润色，不做事实判断；
    而且我们不止教学生看懂代码，更教他们学会设计。"
```

> **第 4 / 5 步是现在唯一"能当场演示完整闭环"的培训环节**（阶段三、阶段六还没做）。
> 被问到"培训功能做到哪了"时，就按它讲：**做完了阶段一、二、四 / 五，剩下阶段三（流程推演）与阶段六（重构挑战）是下一步**——
> 不要用一档 / 二档的排序表去暗示六阶段都在。

**演示前必须做的准备：**

- 提前把分析结果缓存好，**现场不跑实时分析**；
- 业务图谱和设计画布的演示数据提前准备好，不要现场从零开始；
- 准备离线版本，假设现场没有网；
- 浏览器只开一个标签页，关掉无关窗口和通知；
- 提前录屏备用。

### 15.4 翻车预案

| 情况 | 怎么处理 |
|---|---|
| 分析卡住 / 报错 | 立刻切到预生成缓存，说「现场这台机器环境不一样，我用预生成的结果继续演示」，**不要现场 debug** |
| 错误率数字难看 | 主动说出来 + 归因 + 说改法。这是加分项 |
| 评委问 Java 支持 | 见 15.2，诚实 + 讲培养模式的跨语言性 |
| 评委说「见过类似工具」 | 不争论，说差异点：他们的落点是图，我们的落点是教学材料 + 设计能力培养 |
| 时间被压缩到 3 分钟 | 只讲：定位 → 双图模型 → 设计画布演示 → 实测证据 → 诚实边界，其他全砍 |
| 被问到 Roadmap 上还没做的事 | 「这个还没开始做」，**不要现场编** |
| 设计画布 Demo 出错 | 「这是我们最新在做的模块，还在原型阶段」，切到提前准备的反馈截图，**不要硬撑** |
| 被质疑「设计反馈是硬编码的吧」 | 诚实回答反馈模板与匹配逻辑的现状，并说清完整 Rubric 引擎的计划阶段。**原型阶段，诚实比「看起来很智能」更重要** |
| 被质疑「业务图谱是自动生成的吗」 | 分清「演示用的是教师审核版」与「系统具备自动生成初始版能力」两件事 |
| **阶段一 / 二页签点开报"不可用"** | 先看横幅：这是**离线演示模式**（后端没起）。两种处理：① 改用业务图谱 / 项目地图继续讲（离线可用）；② 起后端后**必须重启**再试——`uvicorn` 启动命令没有 `--reload`，改了后端不重启会出现"新接口 404、`/api/health` 版本号还是旧的"（Sprint 4 实测踩到，见 19.5）。**别把这两种情况说成"功能没做"** |
| 被问「离线为什么阶段二整页不可用」 | 如实答：题目与比对都从后端现算，演示快照里**不存第二份题目定义**——否则换问法时两边会不一致（0.3 的表格写了边界） |
| 被问「系统能判断学生答得对不对吗」 | **不能，也不打算说能**：规则引擎只判「你写的话里有没有出现卡片上这些事实」，命中 ≠ 理解（抄卡片也能命中）。见 13.3 |

### 15.5 答辩结束前必须说的一段话（留 20 秒）

> 「最后想说一句实话：我们现在还没有真实教师用户，引擎也还有明显的短板——
> 语义层靠推断、只支持 Python、真实第三方项目上只能退回英文域名、设计层还没开始做。
> 但我们用 3 个真实第三方项目做了实测，能机器核验的数字都在这份材料里。
> **我们不想把没做到的事说成做到了，因为教育场景里，讲错一件事比不讲危害更大。**
> 而我们真正想做的事情，也不只是一个代码分析工具——
> 而是一套完整的业务逻辑思维培养体系，让学生从『看懂代码』走到『自己会设计』。
> 代码分析只是基础，设计能力才是真正的护城河。」
